# goal 条件の書き方

計画の各作業の `goal` は、実装担当（implementer）が自分を追い込むための完了条件です。Claude Code の `/goal` と同じ考え方で書きます。合否を決めるのは goal の文ではなく、ランナーの機械検証（`verify` の実行、変更の範囲、テストの弱体化、実行されて合格したテストでの受入基準の照合）と独立レビューです。だから goal には、ランナーと同じ物差し（コマンドの結果・テスト名に入れた番号）で書きます。「正しく動く」のような条件は、実装担当が何をすれば終わりかを判断できません。

## 必須の4要素

1. **測定できる終了状態**: 「実装が完了」ではなく「AC-3 のテストが存在し pass する」
2. **証明方法**: 実行するコマンドをバッククォートで囲み、期待する結果を書く（「`pnpm verify` が exit 0」）
3. **制約**: 壊してはいけないこと（「既存テストの削除・skip・期待値の緩和はしない」「owns 外のファイルは変更しない」）
4. **ターン上限**: 「または 25 ターンで停止」。上限のない goal は作らない

`pnpm devkit check` は、4要素の **書き方** を機械的に確かめます（内容の妥当さは確かめないので、そこは plan-reviewer が見ます）。

| 要素 | check が探す書き方 |
| --- | --- |
| 終了状態 | `exit 0`、`pass`（単語として。`password` は数えない）、「が通る」「成功する」「エラー 0」「0 件」 |
| 証明方法 | バッククォートで囲んだコマンド |
| 制約 | 「削除・skip・only・緩和 … しない／禁止」か「owns 外 … 変更しない／触らない」。機能の説明に出てくる「削除」だけでは数えない |
| ターン上限 | 「または N ターン」か「N ターンで停止」。「3回」のような回数は数えない |

下のテンプレートの文言を使えば、すべて満たします。

条件文は 4,000 文字以内（`/goal` の上限）。仕様の詳細は仕様書に書き、goal からは `AC-n` などの番号で参照します。

## テンプレート

```
{対象}に {仕様書のパス} の {AC/BR の番号} が実装され、以下をすべて満たす:
(1) `pnpm verify` が exit 0。
(2) {AC-n} のテスト（テスト名に "AC-n" を含む）が {テストファイル} に存在し pass する。テストには「{具体的な境界値の例}」を含む。
(3) {構造上の要求があれば。例: 金額計算は src/server/expense.ts の関数に集約する}。
既存テストの削除・skip・期待値の緩和はしない。owns 外のファイルは変更しない。
または {N} ターンで停止。
```

## 例

```
src/server/approval.ts に docs/spec/expense-app.md の AC-4〜AC-6 と BR-2 が実装され、以下をすべて満たす:
(1) `pnpm verify` が exit 0。
(2) テスト名に "AC-4" "AC-5" "AC-6" "BR-2" を含むテストが tests/unit/approval.test.ts に存在し pass する。BR-2 のテストには「申請額 99,999 円は課長承認のみ、100,000 円は部長承認も必要」の境界値を含む。
(3) 承認状態の遷移は src/server/approval.ts の transition() だけで行う。
既存テストの削除・skip・期待値の緩和はしない。owns 外のファイルは変更しない。
または 25 ターンで停止。
```

## 分け方の目安

- 1 goal = 人間が1回でレビューできる量（AC 2〜5個程度）
- 「アプリを完成させる」のような大きな goal は作らない。ノードを分ける
- E2E を条件にするのは最後の結合ノードだけ（各ノードは `pnpm verify` で十分）

## 書いてはいけない goal

| 悪い例                               | なぜ駄目か                                | 直し方                                          |
| ------------------------------------ | ----------------------------------------- | ----------------------------------------------- |
| 「画面が完成している」「使いやすい」 | 何をすれば終わりか判断できない           | テストやビルドの結果に置き換える                |
| 制約がない                           | テストの削除・skip で条件を満たせてしまう | 制約の文を必ず入れる                            |
| ターン上限がない                     | 迷走したときに止まらない                  | 「または N ターンで停止」                       |
| 仕様をすべて goal に書く             | 4,000 文字の上限、条件の肥大化            | 仕様書に書いて番号で参照する                    |
| 「本番にデプロイする」               | 自動実行に本番操作を含めるのは危険        | goal はテストとビルドまで。デプロイは人間が行う |

## 自分で `/goal` を使うとき

計画の外で単発の作業を任せるときも同じ書き方をします。ノードの条件をそのまま使う場合は `pnpm devkit goal <ID>` で出た行を貼り付けます。進捗は引数なしの `/goal`、中止は `/goal clear` です。席を離れて任せる場合は auto モードで実行してください（goal は権限を広げないので、確認が必要な操作のたびに止まります）。
