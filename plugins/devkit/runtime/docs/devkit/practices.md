# 作業の作法（devkit のスキル）

ランナー（`pnpm devkit run`）が「何をどの順で進め、合格をどう決めるか」を決めるのに対して、ここに挙げるスキルは「1つの作業の中でどう進めるか」を決めます。どれも devkit に同梱されていて、追加のインストールは要りません。

## スキルと、使われる場面

| スキル | 使われる場面 | 要点 |
| --- | --- | --- |
| `devkit-requirements` | kickoff の要件の聞き出しと仕様書 | 聞く前に調べる。なぜ作るのかを最初に確かめる。質問は1回に1問、答えで作るものが変わるものだけ。方式を推奨つきで示して選んでもらう。仕様書は `spec-reader` と読み合わせてから渡す。承認まで何も作らない |
| `devkit-tdd` | すべての実装（implementer には最初から読み込まれている） | 失敗するテストを先に書き、期待どおりに落ちるのを見てから最小の実装で通す。期待値は手で求める。DB は PGlite の実物を使い、モックは外部のものだけ。仕上げに変異チェック |
| `devkit-debugging` | テストの失敗、不具合、統合の失敗、再計画（replanner には最初から読み込まれている） | 根本原因を見つける前に直さない。再現 → 比較 → 仮説を1つずつ → 失敗するテストを書いてから修正1つ。3回直らなければ設計を疑い、人に相談する |
| `devkit-verification` | 完了の主張、コミット、PR、作業の完了報告の前（implementer には最初から読み込まれている） | その場で実行した検証コマンドの出力なしに完了を言わない。エージェントの成功報告は自分で確かめる |
| `devkit-diagnose` | 自走がうまくいかなかったとき | progress.md・graph.json・セッションの記録を読み、`ファイル:行` の根拠つきで報告を `.devkit/diagnosis/` に書く。直すのは報告のあと |
| `devkit-skill-authoring` | devkit のスキルやエージェントを作る・直すとき | スキルなしで失敗するのを見てから書く。description には「いつ使うか」だけを書く。失敗の種類に合わせて書き方を選ぶ |

## エージェントに組み込んだ作法

| エージェント | 組み込んだこと |
| --- | --- |
| `implementer` | 着手前に作業を「テスト → 実装 → 整理」の小さな単位に分ける。レビューの差し戻しは、鵜呑みにせず確かめてから直し、誤った指摘には根拠で答える |
| `reviewer` | ランナーの機械検証に合格した差分について、仕様との整合（足りない・余計・取り違え）と品質（Critical / Important / Minor）を判定する。実装者の説明を理由に指摘を軽くしない。Critical・Important があれば差し戻す |
| `spec-reader` | 仕様書を「書いた人に質問できない実装者」として読み、計画の前に必要な質問だけを返す |
| `final-reviewer` | ミッション全体の差分を最終レビューし、ノードをまたぐ問題と、積み残した Minor の指摘を振り分ける |

## ランナーに組み込んだ作法

- **判断の記録**: 利用者に聞かずに決めたこと（分割の仕方、仕様の読み方など）は、再計画の担当なら構造化出力の `decisions` で返し、ランナーが `.devkit/progress.md` に「判断:」として残す（メインセッションでは `pnpm -s devkit log "判断: …"`）。実行のまとめに一覧が載り、利用者は違うところを直せる。
- **最終レビューの修正は1回**: 最終レビューの指摘は、再計画で修正の作業にまとめて直す（`limits.maxFinalFixRounds`、既定1回）。残った指摘は人間ゲートの確認資料に載る。
- **ブランチの仕上げ**: 選択肢は「PR を作る」か「ブランチを残す」だけ。main へのマージは人が PR で行う。

## 由来

これらは [obra/superpowers](https://github.com/obra/superpowers) v7.0.2（MIT ライセンス）のスキルを、devkit の流れと標準スタックに合わせて日本語で翻案したものです。devkit は superpowers 本体には依存していません。元のファイルとの対応とライセンス表示は `THIRD_PARTY_NOTICES.md` にあります。

superpowers のうち、計画づくりと実行の系統（writing-plans、subagent-driven-development、executing-plans、dispatching-parallel-agents、using-git-worktrees）は取り込んでいません。devkit の計画（graph）・ランナー・作業ディレクトリと検証の隔離が同じ役割を受け持つためです。ただし、評価者の観点（仕様との整合と品質の2段階）、最終レビュー、判断の記録といった考え方は取り込んでいます。

## 上流の更新を取り込むとき

superpowers の新しい版で改善があった場合は、[リリースノート](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md) を読み、該当する devkit のスキルに反映します。手順は `devkit-skill-authoring` に従い、`THIRD_PARTY_NOTICES.md` の版とコミットを更新し、ADR に記録します。
