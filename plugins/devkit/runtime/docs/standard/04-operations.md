# 4. 運用標準

本番でどう動かすかの基準を決める。運用レベルは技術の問題ではなく業務の判断なので、計画を作るとき（kickoff）に業務担当者に業務の言葉で聞き、`docs/profile.json` の `tier` に記録する。

## 案件プロファイル（docs/profile.json）

| 項目 | 内容 |
|---|---|
| `project` | 案件名 |
| `owners.business` / `owners.technical` | 業務担当者と技術担当者（標準オーナー）の `{ name, email }`。リリース前に必須 |
| `tier` | 運用レベル（`lite` / `standard` / `ha`） |
| `users` | 誰が何人くらい使うか |
| `personalData` | 個人情報を保存するか（`stored`）と、その項目（`items`） |
| `auth` | 認証方式（`dev` / `none` / `better-auth` / `sso-entra` / `sso-google` / `sso-lineworks`） |
| `externalHosts` | 接続してよい外部のホスト（`api.example.co.jp`・`*.example.co.jp`）。ここにない接続先を加えると ESC-02 のフラグ |
| `released` | 本番にリリースしたか |
| `releasedMigration` | 本番に適用済みの最後のマイグレーション名（例: `0003_add_status`） |

プロファイルの変更は技術ゲートで確かめる（SEC-12）。

## 運用レベルの選び方（業務担当者への質問）

| 質問 | lite | standard | ha |
|---|---|---|---|
| 止まったら、業務は何時間まで回りますか | 1営業日くらいなら待てる | 数時間なら待てる | 数十分でも困る |
| 最悪、どこまでのデータが消えても許せますか | 前日の夜まで戻ればよい | 1時間以内 | ほぼ失えない |
| 誰が使いますか | 社内の1部署 | 全社・社外の取引先 | 顧客向けのサービス |

迷ったら低い方を選び、利用が広がったら上げる（上げることはできる。下げる必要はほぼない）。

## 運用レベル別の必須事項（OPS-06）

| 項目 | lite | standard | ha |
|---|---|---|---|
| アプリの実行 | 単一のコンテナ | マネージドのコンテナ（AWS なら ECS Fargate） | 2つ以上のタスクを複数の AZ に置く |
| DB | 単一の PostgreSQL | マネージドの DB（RDS など） | Multi-AZ の DB |
| バックアップ | 日次のバックアップ | ポイントインタイムリカバリ（PITR） | PITR＋別リージョンへの複製 |
| 復元の演習 | リリース前に1回 | 半年に1回 | 四半期に1回＋DR の演習 |
| 監視 | ヘルスチェック（`/api/health`）の死活監視 | エラー率・応答時間・DB 接続の監視と通知 | SLO（可用性 99.9%・p95 500ms）と詳しい通知 |
| リリース | 本番に直接 | ステージングで確かめてから本番 | 段階的なリリースとすぐの切り戻し |
| 目安（RPO / RTO） | 24時間 / 1営業日 | 1時間 / 4時間 | 数分 / 1時間 |

どのレベルでも、認証・認可・通信の暗号化・バックアップ・基本のテストは省かない。違うのは冗長化と自動化の程度だけ。

## ルール

- **OPS-01** 案件プロファイルを宣言する。リリース前に案件名と担当者（名前とメール）を記入する
- **OPS-02** `GET /api/health` を用意する。DB 接続を確かめて 200（失敗なら 503）を返し、`allowAnonymous` で公開を明示する
- **OPS-03** 本番のマイグレーションはデプロイの手順で人が `pnpm db:migrate` を実行する。アプリの起動時（コードの migrator。`src/` の外のコードも対象・Dockerfile の CMD / ENTRYPOINT・compose の command・package.json の start）に適用しない。テストと E2E の PGlite は起動時に適用してよい
- **OPS-04** 本番リリース後（`released: true`）は `releasedMigration` を必ず書く。それより後のマイグレーションで、削除（DROP TABLE・COLUMN・CONSTRAINT・INDEX・VIEW・TYPE・SCHEMA・FUNCTION・TRIGGER・POLICY など。COLUMN を省いた `ALTER TABLE … DROP` や、ADD と並べた DROP も）・TRUNCATE・DELETE・名前の変更・型の変更（COLUMN を省いた `ALTER … TYPE` も）をしない。`$$` の中（関数や DO の本体）と `EXECUTE` の文字列も対象で、中身を読めない動的な SQL（`EXECUTE format(…)` など）は使わない。文字列とコメントの中、引用符の中の識別子（列名 "truncate" など）は対象外。追加→移行→削除の段階的な変更（expand-contract）にする。適用済みのマイグレーションのファイルは変えない・消さない（差分で検出する）
- **OPS-05** 本番リリース前に `docs/runbook.md` の必須の見出し（起動と停止・デプロイ・マイグレーション・バックアップと復元・監視と通知・障害時の連絡先）をすべて埋める（「（記入）」「未記入」が残っていたら未完了）
- **OPS-06** 運用レベル別の必須事項を、本番リリース前の技術ゲートで確かめる
- **OPS-07** デプロイ・本番 DB の操作・クラウドの設定変更・シークレットの操作は人が行う

## リリースの流れ

1. 最後のマイルストーン（受け入れ）で、AI が `docs/runbook.md` の技術的な手順（起動と停止・デプロイ・マイグレーション）を下書きし、人が体制に関わる節（バックアップ・監視・連絡先）を書く
2. `pnpm standard:release`（SEC-09・OPS-05、期限切れの例外を含む）が通ることを確かめる
3. 業務担当者が業務ゲート、標準オーナーが技術ゲート（上の必須事項を含む）を承認する
4. 人が Docker イメージを作ってデプロイし、本番の DB に `pnpm db:migrate` を実行する
5. 本番に出したら `docs/profile.json` の `released` を true にし、`releasedMigration` に最後に適用したマイグレーション名を書く（以降は OPS-04 が有効になる）

本番のインフラ（クラウドのリソース）は、標準オーナーが案件ごとに用意し、手順を runbook に残す。
