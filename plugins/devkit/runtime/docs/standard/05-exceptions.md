# 5. 例外ルール

標準で決められない場面は必ず出る。そのとき AI エージェントは**自分で決めずに止まり**、判断を人に渡す。人が判断する場面を「標準の例外」だけに絞るためのルール。

## 止まる条件

| ID | 止まる条件 | 判断する人 | 依頼の種別 |
|---|---|---|---|
| ESC-01 | 許可リストにない依存・ツール・クラウドサービスが必要 | 標準オーナー | 技術 |
| ESC-02 | 新しい外部の接続先が必要（URL・ホスト名・IP。src の外の設定ファイル・`.env` の `KEY=ホスト`・`public/` も対象。`src/server/external/` の外からの外部呼び出し（fetch とその別名・WebSocket など）、ネットワークや外部コマンド（child_process）のパッケージ、外部連携のコードの変更を検出したら技術ゲートで確かめる） | 標準オーナー | 技術 |
| ESC-03 | 権限表を変える（`permissions.ts` と、それが読み込むファイルの変更を検出したら業務ゲートで確かめる） | 業務担当者 | 業務 |
| ESC-04 | 業務ルールが仕様になく、仕様の「前提」でも決められない | 業務担当者 | 業務 |
| ESC-05 | 標準・仕様・計画・案件プロファイル・例外・設定ファイルの変更が必要 | 標準オーナー | 技術 |

ほかに、個人情報の項目の追加（SEC-08）、安全の仕組みの中心のファイルの変更（SEC-12）、データモデルの変更（DATA）、依存の変更（DEPS）も、変更を検出したら技術ゲートで確かめる。差分を正しく取れないときは、安全側に倒して技術ゲートでの確認を必須にする。

保護ファイル（ESC-05）をエージェントが変えた場合、ランナーはその試行の開始時の内容に戻し、その試行を不合格にする。

## 判断依頼の出し方（AI エージェント）

実装せずに、次の形式で判断依頼を書いて作業を終える。置き場所と回答の受け取り方はランナーの説明（`docs/devkit/`）に従う。

```markdown
種別: 技術        ← 「業務」か「技術」
条件: ESC-01      ← 当てはまる止まる条件
## 何が必要か
## なぜ必要か（標準の範囲で試したこと）
## 選択肢（それぞれの影響・費用・危険）
## おすすめと理由
```

| 項目 | 書くこと |
|---|---|
| 種別 | 業務（業務担当者が答える）か技術（標準オーナーが答える） |
| 条件 | ESC-01〜05 のどれに当たるか |
| 何が必要か | 欲しいもの（依存の名前と版、接続先のホスト、変えたい権限など）を具体的に |
| なぜか | 仕様のどの AC・BR のためか。標準の範囲で試したことと、それでは足りない理由 |
| 選択肢 | 2つ以上。それぞれの影響・費用・危険。「やらない」も選択肢に入れる |
| おすすめ | どれをすすめるかと、その理由 |

ランナーは判断依頼を見つけると止まり、種別に応じて業務担当者か標準オーナーに回す。回答は `docs/decisions.md` に記録される。

## 例外の承認（標準オーナー）

1. `docs/adr/` に ADR を1枚書く（`docs/adr/_template.md`。背景・決定・検討した選択肢・影響・見直す時期）
2. `docs/exceptions.json` に例外を登録する
3. 標準チェッカーは、登録された例外の対象を違反として扱わない

例外の記録には次の項目が必須（**ESC-06**）。欠けている例外は適用されず、ESC-06 の違反として表示される。

| 項目 | 内容 |
|---|---|
| `id` | `EXC-001` のような連番（重複しない） |
| `rules` | 対象のルール ID の配列（標準にあるもの。ESC-06 は入れられない） |
| `subject` | 対象（下の表）。ルール全体を外すときは `"*"` |
| `reason` | 一行の理由 |
| `adr` | ADR のパス（案件の中に存在するファイル） |
| `approvedBy` / `approvedAt` | 承認した標準オーナーと日付（実在する日付 YYYY-MM-DD。未来の日付は不可） |
| `reviewBy` | 見直しの期限（実在する日付。approvedAt 以降）。過ぎると普段は注意、リリース前の検査では違反になる |

| subject | 対象 | 例 |
|---|---|---|
| `dependency:<パッケージ名>` | 依存（TECH-01・TECH-02） | `dependency:exceljs` |
| `host:<ホスト名>` | 外部の接続先（ESC-02。普段は profile の externalHosts に登録する） | `host:api.partner.co.jp` |
| `file:<パス>` | ファイル（そのファイルの違反） | `file:src/app/print/page.tsx` |
| `migration:<ファイル名>` | マイグレーション（OPS-04） | `migration:0007_drop_legacy.sql` |
| `auth:none` | 認証なしの公開（SEC-09） | `auth:none` |

```json
{
  "exceptions": [
    {
      "id": "EXC-001",
      "rules": ["TECH-01", "TECH-02"],
      "subject": "dependency:exceljs",
      "reason": "既存の Excel 台帳を取り込むため",
      "adr": "docs/adr/0004-exceljs.md",
      "approvedBy": "技術 花子",
      "approvedAt": "2026-11-09",
      "reviewBy": "2027-05-31"
    }
  ]
}
```

- `subject: "*"`（ルール全体をこの案件では検査しない）は、既存のシステムに devkit を入れた場合などに限る。検査のたびに注意として表示される
- 例外はフラグ（人間ゲートでの確認）を消さない。ただし `host:<ホスト名>` の例外は、そのホストの ESC-02 のフラグを出さない
- `docs/exceptions.json` の変更は、技術ゲートで確かめる（SEC-12）
- 例外は案件の中だけで有効。同じ例外が3つ以上の案件で出たら、標準そのものを改訂する候補にする

## 人に残る判断

標準があっても、次は人が判断する。

- 標準の承認と改訂（標準オーナー）
- 本番リリースの最終の承認と、障害時の連絡先（標準オーナー。AI は責任を負う主体になれない）
- 個人情報や契約に関わる判断（必要に応じて法務・管理部門に確かめる）
