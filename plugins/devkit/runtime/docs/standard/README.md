# 社内標準（devkit 標準）

版: `2026.11.2`（[VERSION](VERSION)）／ 管理: 標準オーナー（案件では `docs/profile.json` の `owners.technical`）

Claude Code で開発する案件は、技術の判断をこの標準に従って行う。業務担当者は「何を・なぜ作るか」の判断に集中し、AI エージェントは「どう作るか」を標準の範囲で受け持つ。標準で決められないことは、AI が自分で決めずに止まり、人に判断を求める（[5. 例外ルール](05-exceptions.md)）。

技術の選び方と、AI がよく間違える点は `docs/devkit/stack.md` にある。この標準はそこから「守ること」と「確かめ方」を決める。

## 構成（5層）

| 層 | 文書 | 決めていること |
|---|---|---|
| 1 | [技術標準](01-technology.md) | 使う技術・バージョン・使わない技術（許可リスト: [dependencies.json](dependencies.json)） |
| 2 | [設計標準](02-design.md) | 置き場所と実装の型（defineAction・入口のガード・権限表・サーバー処理） |
| 3 | [品質・セキュリティ基準](03-quality-security.md) | 完了の定義・テスト・セキュリティ（OWASP ASVS 5.0 の Level 2 相当）・認証 |
| 4 | [運用標準](04-operations.md) | 運用レベル（lite / standard / ha）と本番の必須事項・リリースの流れ |
| 5 | [例外ルール](05-exceptions.md) | 止まる条件・判断依頼・例外の承認と記録 |

## 規約・雛形・検査

各ルールは「規約（この文書）」「雛形（テンプレートに最初から入っているコード）」「検査（機械かレビューで確かめる方法）」をそろえる。機械で読める一覧は [rules.json](rules.json)。案件では `node scripts/standard/check.mjs --list` で表示できる。

ルール 47 件の確かめ方の内訳: 自動検査 24（うちリリース前の検査 2）、lint 1、ランナーの検証 4、変更検出→人間ゲート 6、独立レビュー（AI） 10、人間ゲート 2。

| 確かめ方 | 誰が・いつ |
|---|---|
| 自動検査 | 標準チェッカー（`pnpm standard:check`）。`pnpm verify` に含まれ、違反があれば失敗する。リリース前の検査は `pnpm standard:release` |
| lint | Biome（`pnpm lint`）。`pnpm verify` に含まれる |
| ランナーの検証 | devkit のランナーが、作業ごとの機械検証で確かめる |
| 変更検出→人間ゲート | 標準チェッカーが差分（`--base`）から検出し、ランナーが業務ゲートか技術ゲートに回す |
| 独立レビュー（AI） | 実装とは別のレビュー役の AI が差分を読む |
| 人間ゲート | 業務担当者か標準オーナーが確かめる |

自動検査は規約をすり抜けにくくする網で、すべての書き方を塞げるわけではない。検査を避ける書き方をすることは禁止で、検査で拾えないものは独立レビューと人間ゲートが確かめる。

## 標準チェッカー

依存パッケージのない Node.js のスクリプト（`scripts/standard/check.mjs`。Node.js 22 以上）。案件のディレクトリ（`docs/standard/rules.json` があるところ）で実行する。ルートは上のディレクトリへ探すが、git のルート（`.git` があるところ）より上には上らない。

検査するのは案件の中のすべてのコード（`.ts`・`.tsx`・`.js`・`.jsx`・`.mjs`・`.cjs` など。`src/` の外も含む）。`node_modules`・`.next*`・`dist`・`build`・`out`・`coverage`・`test-results`・`test-reports`・`playwright-report` などの生成物と、devkit と標準の部品（`.claude/`・`.devkit/`・`scripts/devkit/`・`scripts/standard/`）は、コードの規約の対象から除く（秘密情報の検査は `.claude/` と `.devkit/` も見る）。シンボリックリンクはたどらず、検査できないもの（シンボリックリンク・NUL を含むコード・5MB を超えるコード）は違反にする（ARCH-11）。テストとして扱うのは、ファイル名が `*.test.*`・`*.spec.*` のものと、ルート直下の `tests/`・`e2e/` の中だけ。

| コマンド | すること |
|---|---|
| `node scripts/standard/check.mjs` | 自動検査（`pnpm standard:check`） |
| `node scripts/standard/check.mjs --release` | リリース前の検査を加える（`pnpm standard:release`） |
| `node scripts/standard/check.mjs --base <コミット>` | 差分から人の確認が必要な変更（フラグ）を検出する。比べる先は作業ツリー（未追跡のファイルを含む） |
| `node scripts/standard/check.mjs --base <a> --head <b>` | コミット a と b の差分で検出する |
| `node scripts/standard/check.mjs --json` | 結果を JSON で出す（ランナーが使う） |
| `node scripts/standard/check.mjs --list [--markdown]` | ルールの一覧 |
| `node <新しい版>/scripts/standard/check.mjs --standard <新しい版>/docs/standard` | 案件はそのままで、新しい版の標準で検査する（版を上げる前に、新しく出る違反を確かめる） |

- 終了コード: 0 = 違反なし、1 = 違反あり、2 = 実行できない（引数の誤り・標準が見つからない）。フラグと注意は終了コードに影響しない
- JSON: `{ version, ok, release, checked: [ルール ID], violations: [{ rule, title, file, line, message }], flags: [{ rule, role, title, message, items }], warnings: [{ rule, title, file, message }] }`。flags の role は `business`（業務ゲート）か `technical`（技術ゲート）
- 差分を取れないとき（`--base` の値がない・空・コミットでない、git の失敗）は、取れなかったことを SEC-12 のフラグにして、変更全体を技術ゲートで確かめる（安全側に倒す）
- 検査そのものが失敗したルールは、そのルールの違反として扱う
- テキストの出力の「自動検査 N 項目」は、検査した auto のルールの数（フラグは数えない）
- 出力は書き切ってから終える（大きな JSON をパイプで受けても途中で切れない）

## 役割

| 役割 | 受け持つこと |
|---|---|
| 業務担当者 | 仕様（受け入れ基準・業務ルール・権限表）、運用レベルの選択、業務ゲートの承認、業務の判断依頼への回答 |
| AI エージェント | 標準の範囲での設計・実装・テスト。範囲の外は止まって判断依頼を出す |
| 標準オーナー | 標準の管理と改訂、例外の承認、技術ゲート（データモデル・外部接続・個人情報・安全の仕組み・本番リリース）の承認、障害時の連絡先 |

## 版の扱い

- 版は「年.月.修正番号」（[VERSION](VERSION)）。変更点は [CHANGELOG.md](CHANGELOG.md)
- 案件は作成時の版に固定される（案件の `docs/standard/`）。標準を更新しても、既存の案件は勝手には変わらない
- 新しい版に上げるときは、先に `--standard` で新しく出る違反を確かめ、直してから `docs/standard/` と `scripts/standard/` を差し替える。標準の差し替えは技術ゲートで確かめる（SEC-12）
- 同じ例外が3つ以上の案件で出たら、標準そのものを改訂する候補にする（[5. 例外ルール](05-exceptions.md)）
