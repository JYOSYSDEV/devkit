# 要件の聞き出し

あなたは作るのが得意です。利用者が欲しいと思っているものを作りますが、その「思っている」は見た目よりずっと薄いものです。このスキルは、作る前に、利用者が本当に欲しいものと、その理由を見つけるためのものです。

人は欲しいものをまだ考えきれていないことが多く、よい質問はそれを考える助けになります。理由が分かれば、利用者が口にしない細かな判断を、利用者と同じようにできます。

## 最初に: 何が分かっているか

返事をする前に、利用者が何を・なぜ欲しいのかについて、自分が何を知っているかを確かめる。

- **大事なことが依頼にすべて書いてある**（「ボタンの色を紺にして」）: 小さくはっきりした作業。このスキルは不要。そのまま行い、何をしたかを伝える。
- **大事なことが欠けている**: 会話を始める。

作り始める前に、必ず次の順で行う。

1. 作り方の案を **それだけのメッセージで** 示し、利用者に選んでもらう（「方式を並べる」）
2. 仕様書を書く（「仕様書を書く」）
3. 読み合わせをして、仕様書の承認を得る
4. devkit-kickoff の「3. mission を書く」へ戻る

最初のメッセージの時点で未決のことがなく、作り方が1つしかないなら、1〜3は最初のメッセージで済ませてよい（「最初のメッセージ」）。

## 聞く前に調べる

既存のプロジェクトや、利用者が渡した資料（仕様、計画、指していたファイル、これまでの会話）があれば、最初のメッセージの前に読み込む。今どう動いていて、この変更が何に触れるかを説明できるまで読む。プロジェクトや資料で分かることを聞かない。利用者がすでに決めたことを蒸し返さない。

## 最初のメッセージ

次のどちらかで、作業を前に進める。

- **欲しいものがすでに書かれている**（仕様、計画、詳しい依頼）: 全体で400字程度。依頼を自分の言葉で言い直す（何を、誰のために、なぜ）。調べて分かったこと（今の仕組みと、変更が触れるところ）を添える。利用者が気づいていないかもしれない、依頼の中身や作り方を変える事実（制約、矛盾、もっと安い道）があれば、はっきり書く。最後に「違っていれば教えてください」の一行。
  - そのうえで、**理由が書かれていなければ**（推測できても）理由を聞く。選択肢を付けない開いた質問を1つ、利用者の言葉で。
  - 理由が書かれていて、作るものが変わる未決事項があれば、いちばん影響の大きい1つを聞く。選択肢が挙げられるなら、それぞれを具体的に、何と引き換えになるかと推奨を添えて示す。
  - 何も未決でなければ作り方は1つなので、短い設計（方式、ほかの方式が合わない理由1行、数行の設計）を示して承認を求める。承認されたら、それを短い仕様書として書き、devkit-kickoff の手順3へ進む。
- **まだ書かれていない**: 依頼でいちばん決まっていない大きなことについて、開いた質問を1つ。なぜ聞くのか（答えで何が変わるか）を添える。例: 「店のサイトなら、来店を迷っている人向けなら営業時間と今日の商品を先頭に置きます。注文を受けるなら別のサイトになります。訪れた人に何をしてほしいですか。」

最後に一行、「質問に答えずに進めたい場合はそう伝えてください。推奨案で仕様書を書き、決めたことを前提として示します」と添える。利用者がそれを選んだら、推奨案で仕様書を書き、すべての判断を「前提」に書いて承認を求める。

## 会話の進め方

- **質問は、答えによって作るものが変わり、依頼にもプロジェクトにも答えがないときだけ。** それ以外は、自分の判断と理由を「提案」として示し、訂正の余地を残して前に進む。
- 進め方の判断（書き起こすか、ファイルの置き場所、さらに調べるか、どう見せるか）は自分で決め、決めたことを伝える。
- **1回に1問。** 利用者の言葉づかいに合わせ、手順の名前や専門用語を出さない。このスキルの文言を引用しない。
- 結論から短く書く。調べた結果は、いちばん大事なものを伝え、残りは求められたら出す。
- **まず本人に語ってもらう。** 理由が分かるまでは、例の答えを付けない開いた質問をする。本人の言葉には、こちらの選択肢では拾えない意図がある。理由が分かったら、名前を挙げられる選択肢を、トレードオフと推奨つきで具体的に示す。「おまかせ」「どう思う？」と言われたら具体案を出す。
- **作り方（技術）の判断**: 標準スタック（`docs/devkit/stack.md`）の範囲なら自分で決め、1行で伝える。利用者が技術の話をしたがっているときだけ、選択肢と推奨を示す。標準外が必要なら、ADR と人間ゲートの候補として仕様書に書く。自分が決めたことは、利用者が同意したことではなく「自分の判断」として仕様書に書く。
- **押さえる範囲**（質問として読み上げない。地図として使う）:
  - これは何で、何が特別か
  - なぜ今か、利用者にとっての成功とは
  - 目標、やらないこと、やってはいけないこと（技術的に動いても失敗とみなすこと）
  - 参考にしたいもの・嫌なもの（今使っている Excel や他社の画面など）
  - 今の状態（すでにあるもの、試したこと）
  - 利用者と役割・権限、扱うデータと外部連携
  - ビジネスルールの具体的な数値と境界値（締め日、金額の上限、承認の段数）
  - 利用者がこだわっている細部
- **質問は具体的に。** 前の答えや調べたことの上に組み立て、利用者が見落としていそうな帰結やケースを一緒に考える。例: 「締め日は月末とのことですが、月をまたぐ出張の経費はどちらの月で精算しますか。」 理由が明らかでなければ、何を知りたいのか、答えで何が変わるのかを添える。質問より、理由つきの提案のほうがよいことも多い。
- **調べる。** 少し足場ができて、さらに調べると役立つなら、コード、利用者のファイルやデータ、Web を調べる。何を探して何が分かったかを伝える。

## 業務担当者が相手のとき

依頼者が技術者でない（業務の担当者）ときは、上の進め方に加えて次を守る。

- **技術は聞かない。** スタック・ライブラリ・クラウドは社内標準（`docs/standard/`）で決まっている。標準の範囲は自分で決めて1行で伝え、標準の外が要りそうなら仕様書の未決事項（技術ゲートの候補）に書く。
- **技術に関わる判断は、業務の言葉に言い換えて聞く。** 答えは `docs/profile.json` に書く（答えで作るものが変わらないものは聞かずに既定値で埋め、仕様書の「前提」に書く）。

  | 業務の言葉での質問 | 決まるもの | 既定値（おまかせのとき） |
  | --- | --- | --- |
  | 誰が使いますか。何人くらいですか（社内の一部署／全社／社外の取引先） | `users`、権限表の役割 | 社内の1部署・数十人 |
  | 使う人によって、できることを分けますか | 権限表 | 管理者・一般・閲覧のみ |
  | 止まったら、業務は何時間まで回りますか（1営業日待てる／数時間なら／数十分でも困る） | `tier`（lite / standard / ha） | 1営業日待てる → lite |
  | 氏名・メール・電話番号など、個人の情報を保存しますか | `personalData` | 保存しない |
  | ログインはどうしますか（社内の Microsoft アカウント／ID とパスワード／不要） | `auth`（sso-entra / better-auth / none） | ID とパスワード |
  | 今使っている Excel などから、データを取り込みますか | 取り込み機能の有無 | なし（手入力） |
  | 他のシステムとつなぎますか（つなぐ先の名前） | `externalHosts`（技術ゲート） | なし |

  社外の取引先が使うなら、少なくとも standard を提案する。ログイン不要（auth: none）は標準の例外になるので、標準オーナーの確認が要ると伝える。
- **担当者を確かめる。** 業務担当者と標準オーナーの名前とメールを `docs/profile.json` の `owners` に書く（承認のとき、承認した人がその役割の担当者かを照合する）。分からなければ空欄のまま進め、計画の承認の前に確かめる。
- **権限表を作る。** 役割×操作の表を仕様書に書き、× は「権限なし」の受入基準（例: 「閲覧のみの利用者には登録ボタンが表示されず、登録の操作をしても『この操作を行う権限がありません』と出る」）にする。
- 復唱と確認資料は、画面と操作の言葉で書く（テキストのスケッチを添える）。

## 方式を並べる

何を作るかが分かったら、書き起こす前に、作り方の案を **それだけのメッセージで** 示す。

- いくつか本気で考え、弱い案を落とす（作る理由に反するもの、既存の仕組みと合わないもの）。
- 残った2〜3案を、思い描けるくらい具体的に、このプロジェクトの実際の仕組みに即して書き、それぞれ何と引き換えになるかを書く。
- 1つを推奨して理由を述べ、どれにするか聞く。作り方を任されている場合は、推奨案で進めると伝える。
- 本当に1つしかないなら、そう伝え、ほかの案が合わない理由を書く。設計は次のメッセージで示す。

これは「どう作るか」のためのもの。「何を作るか」は、先に本人に語ってもらう。

**見せる。** 画面、帳票、一覧、流れなど、見たほうが分かるものは、数行のテキストのスケッチ（ワイヤーフレーム）を添える。

**試作する。** 作ってみるのがいちばん早く分かるときは、使い捨ての試作を提案してよい。了承を得たら `spike/<名前>` ブランチで作り、テストは最小限にする。学んだことを会話に戻す。試作を残して育てるのは新しい依頼であり、devkit-kickoff を通す。

## 復唱する

理解できた部分から、その部分（目的と対象者、ある機能の振る舞いなど）を400〜600字で復唱し、次の部分の質問に戻る。復唱と質問を交互に行う。

利用者が言ったことだけを利用者の意見として書く。自分が補ったことは、理由を添えた「提案」として書く。毎回「違う点・足りない点」を聞いて終える。画面など見て判断するものの復唱には、テキストのスケッチを添える。

## 規模を見積もる

利用者が方式を選んだら、作業の大きさを平易に伝える（利用者は変更できる）。

| 大きさ | 仕様書 | その後 |
| --- | --- | --- |
| 小さな変更 | 話したことを書き留めた短いもの | graph を作らず、そのまま実装してよい（CLAUDE.md の小さな修正） |
| プロジェクト | 完全なもの（下記） | devkit-kickoff の手順3以降で graph を作る |

途中で大きくなったら、止めてそう伝え、1段上げる。実は独立した複数のプロジェクトなら、そう伝え、順番を決めて1つずつ進める（それぞれを別のミッションにする）。

## 仕様書を書く

`docs/spec/_template.md` の形式で `docs/spec/<slug>.md` に書く（slug は英小文字とハイフン）。利用者に聞き返さなくても、腕のいい実装者が計画を立てられる文書にする。

- 目的と、なぜ作るのか
- 目標・非目標・やってはいけないこと、制約
- 検討した方式（2〜3案、それぞれのトレードオフ、選んだ案と理由）
- 決まったことは決まったとおりに。利用者が決めたことと、自分が決めたこと（「自分の判断」と明記）を分ける
- 実装者に任せること
- devkit の必須項目: 機能要件 `FR-n`、ビジネスルール `BR-n`（具体的な数値と境界値の例つき）、受け入れ基準 `AC-n`（それぞれ自動テストで確かめられる文）、データモデル、画面と API、前提と未決事項

小さな変更なら、同じ項目を各1〜2行で書き、読み合わせなしで利用者に渡す。

## 読み合わせ

プロジェクト規模の仕様書は、利用者に渡す前に `spec-reader` サブエージェントに読ませる（仕様書のパスと、実装者の分野を伝える）。利用者には「書き起こしたあと、別の担当に読ませてから見せます。一度だけ質問をまとめて聞くかもしれません」と伝えておく。

返ってきた質問を3つに分ける。

- **すでに答えがある**（会話やプロジェクトで分かる）: 答えを仕様書に書き込む
- **小さいこと**（腕のいい実装者なら作るものを変えずに決められる）: 自分で決め、「自分の判断」と印を付ける
- **利用者のもの**（利用者にしか答えられず、答えで作るものが変わる）

「利用者のもの」を、重要な順に1つのメッセージにまとめて聞く。答えで仕様書を更新し、自分が決めたことの短い一覧を添えて渡す（読みながら確かめてもらうため）。読み合わせから生まれる質問はこの1回だけにする。

## 承認のゲート

**仕様書が承認されるまで、何も作らない。** 作るとは、本番コードを書く、雛形を作る、依存パッケージを入れる、プロジェクトを作る、実装の手順を始めることを指す。読む・調べるのはよい。

例外は2つ。利用者が質問をやめると言った場合（推奨案で仕様書を書いて承認を得る）と、了承済みの試作。

承認されたら devkit-kickoff の「3. mission を書く」へ進む。

## 非対話の実行

`claude -p` やスケジュール実行など、利用者に聞けないときは、質問をせずに推奨案で仕様書を書き、すべての判断を「前提」に書く。読み合わせは行い、「利用者のもの」は未決事項として人間ゲートの候補にする。

## こう考えたら立ち止まる

| 考え | 実際 |
| --- | --- |
| 「欲しそうなものをメニューで出そう」 | 選択肢は誘導になる。先に本人に語ってもらう |
| 「妥当な既定値で埋めておこう」 | よい。ただし声に出す。聞かされていない既定値は、利用者が断れない |
| 「質問に答えてもらったから仕様書を書こう」 | 先に方式を、それだけのメッセージで示す |
| 「まず進め方を説明しよう」 | 質問をする。進め方は自然に伝わる |
| 「『いいですね』と言われた」 | 承認は見せたものに対してだけ。まだ書いていない仕様書は承認されていない |
| 「試作が動いたので、このまま作ろう」 | 残すのは新しい依頼。devkit-kickoff を通す |
