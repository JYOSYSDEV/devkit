# devkit の不調を調べる

自走がうまくいかなかった理由を、記録を読んで証拠つきで報告します。報告するのが役目で、その場で直すことではありません。直し方は報告のあとで利用者と決めます。

**核心:** 指摘には必ず `ファイル:行`（またはコミット）を付ける。根拠のない指摘は書かない。数字は記録か、自分が実行したコマンドの結果から取る。記憶で書かない。

## 手順（各手順をタスクリストにする）

1. **何が問題かを決める。** 1回に1問で聞き、次を書ける状態にする: 対象のミッション（とノード・サイクル）、期待していたこと、実際に起きたこと、利用者が気にしている観点（かかった時間、使用量、繰り返し、特定の1つの行動）。「時間がかかった」は不満であって、問題の記述ではない。
2. **記録を集める。**
   - `.devkit/progress.md`（ランナーの出来事と「判断:」）、`.devkit/graph.json`（計画）、`.devkit/state.json`（作業ごとの状態・試行回数・ラウンドごとの機械検証とレビューの結果 history・マイルストーンの状態）、`.devkit/controls.json`（計画の承認・記録したゲート・人の承認・回答・サイクル上限）、`.devkit/evidence/`（合格した作業の証拠）、`.devkit/reports/`（実行のまとめ）、`.devkit/proposals/`、`.devkit/requests/`（判断依頼）、`.devkit/journal.jsonl`（人のコマンドが書いたファイルの記録）、`.devkit/reports/tamper-*.md`（改ざんの検出）、`.devkit/learnings.md`、`.devkit/archive/`
   - ランナーのログ: `.devkit/logs/run-<時刻>/`（AI の呼び出しごとの stream-json、コンテナの中の依存のインストール `*-install.log` と検証コマンド `*-verify.log`）。`pnpm -s devkit logs` で要約できる
   - `git log --oneline --graph <統合ブランチ>`、ノードブランチ（`git branch --list '<統合ブランチ>--*'`）、`git worktree list`（レビュー用の取り出し）。AI の作業ディレクトリと取り出しは、リポジトリの外の作業場所（既定 `~/.cache/devkit/<案件>/work`）にある
   - セッションの記録: `~/.claude/projects/` の下の、このリポジトリのパスに対応するディレクトリにある `*.jsonl`（各セッションの会話）。ワークフローの実行ごとのスクリプトもここに保存されている。対象のセッションは、最初の指示と時刻を引用して特定し、候補から外したものは理由を書く
3. **観点ごとに読む。** 記録が長ければ、観点ごとにサブエージェントへ並列に任せてよい（それぞれに問題の記述、読む範囲、下の観点の1つを渡し、`ファイル:行` のない指摘は捨てる）。
   - **計画の守り方**: graph の順序・owns・goal の制約が守られたか。共有ファイルの編集、テストの弱体化、ゲートの飛ばし（`pnpm devkit check` のゲートと承認の食い違い、フックに止められた記録）がなかったか
   - **繰り返し**: 同じ修正の往復、同じテストの失敗、同じ指摘の繰り返し（どのノード・どのラウンドか）
   - **つまずき**: ツールのエラー、権限の確認で止まった箇所、worktree やブランチの扱いの誤り
   - **品質の証拠**: 完了と言った時点で、検証コマンドの出力があったか（`devkit-verification` が守られたか）
   - **指示との食い違い**: 利用者の指示、CLAUDE.md、スキルの手順のどれと食い違ったか
   - **時間と使用量**: どのサイクル・どのノード・どのラウンドに時間と使用量がかかったか。並列数とラウンド数は適切だったか
4. **報告を書く。** `.devkit/diagnosis/<YYYYMMDD>-<短い名前>.md` に次の順で書き、内容を示してパスを伝える。
   1. 問題の記述
   2. 起きたことの時系列（サイクル・ノード・ラウンド単位、根拠つき）
   3. 観点ごとの所見（根拠つき）
   4. 原因の見立て（確からしさ: 確実 / おそらく / 可能性あり）
   5. 再発を防ぐ候補: learnings.md に書くこと、goal・graph の書き方の改善、devkit 自体（スキル・エージェント・devkit.mjs）の改善
   6. 調べられなかったこと
5. **直すかを決める。** 利用者が選んだものだけを行う。learnings.md への追記はその場で、devkit 自体の改善は `devkit-skill-authoring` の手順で行う。

## 注意

- 記録に個人情報や秘密情報が含まれることがある。報告には必要な部分だけを引用し、トークンやパスワードは伏せる。
- 報告を社外（GitHub の issue など）に出すのは、利用者が求め、内容を確認したあとだけにする。
