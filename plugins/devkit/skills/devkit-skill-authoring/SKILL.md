# devkit のスキルを書く・直す

スキルを書くことは、手順書に対するテスト駆動開発です。**スキルなしでエージェントが失敗するのを見ていなければ、そのスキルが正しいことを教えているか分からない。**

社内標準の変更なので、変えたら `docs/adr/` に記録し、テンプレートに反映します。

## スキルにするか、ほかの手段にするか

| 中身 | 置き場所 |
| --- | --- |
| 繰り返し使う技法・判断の手順（直感では分からないもの） | スキル（`.claude/skills/<name>/SKILL.md`） |
| このリポジトリ固有の決まり（書き方、禁止事項） | `CLAUDE.md` |
| 正規表現や検査で機械的に守らせられるもの | フック（`.claude/hooks/`）か `scripts/devkit/devkit.mjs` の検証。文章にしない |
| 一度きりの解決の経緯 | 書かない（必要なら `.devkit/learnings.md`） |
| 決まった役割と道具を持つ作業者 | エージェント（`.claude/agents/<name>.md`） |

## 書き方の決まり

- **名前**: 英小文字・数字・ハイフン。devkit の標準スキルは `devkit-` で始める（個人のスキルと名前がぶつかると個人のものが優先されるため）。
- **description**: **いつ使うか** だけを書く。使う場面・きっかけ・症状を具体的に。手順の要約を書かない（要約を読んだエージェントは、本文を読まずに要約に従ってしまう）。日本語で、利用者が実際に言いそうな言葉を入れる。
- **本文**: 冒頭に核心を1〜2文。早見表、よくある誤り、危険信号を置く。例は1つ、このリポジトリのスタック（TypeScript・Vitest・Drizzle）で。長い参照資料は同じディレクトリの別ファイルに分け、本文から参照する。
- **frontmatter**: Claude Code の項目を使う（`description`、`argument-hint`、`disable-model-invocation`、`allowed-tools` など）。サブエージェントに最初から読み込ませるなら、エージェント側の `skills:` に名前を書く。
- 由来のあるスキル（superpowers から翻案したものなど）を直すときは、末尾の出典表示と `THIRD_PARTY_NOTICES.md` を残す。

## 失敗の種類に合わせて書き方を選ぶ

まず、スキルがないときにエージェントがどう失敗するか（基準の失敗）を分類する。ある失敗に効く書き方は、別の失敗には逆効果になる。

| 基準の失敗 | 合う書き方 | 合わない書き方 |
| --- | --- | --- |
| 分かっているのに、急かされると規則を破る | 禁止 + 言い訳と現実の表 + 危険信号 | 「〜が望ましい」などの柔らかい助言 |
| 従ってはいるが、出力の形が違う（長すぎる、結論が埋もれる） | 出力の形を部品と順番で示す（「出力の形」） | 「〜しない」の禁止の列挙 |
| 作るものから必須の要素が抜ける | テンプレートに必須の欄を設ける | テンプレートの近くに注意書きを足す |
| 条件によって振る舞いを変えたい | 観察できる条件で分岐させる（「仕様書があれば参照する」） | 無条件の規則 + 例外の但し書き |

どの書き方でも、「〜しない。ただし重要な場合を除く」のような含みの但し書きを付けない。本当の例外は、観察できる条件の分岐として別に書く。

## 確かめ方（RED → GREEN → REFACTOR）

1. **RED: スキルなしで試す。** そのスキルが必要になる場面を、サブエージェントに「スキルなし」でやらせる。規律のスキルなら、時間がない・すでに手間をかけた・指示した人が急かす、などの圧力を3つ以上組み合わせる。どう判断したか、どんな言い訳をしたかをそのまま記録する。
2. **GREEN: 最小のスキルを書く。** 記録した失敗と言い訳に対処することだけを書く。起きていない場合のための記述を足さない。同じ場面を「スキルあり」でやらせ、守られることを確かめる。
3. **REFACTOR: 抜け道をふさぐ。** 新しい言い訳が出たら、それへの反論を足して試し直す。

文言の効き目は、場面全体を試す前に小さく確かめる: 同じ課題を、文言なし（対照）と文言ありで、それぞれ5回以上、新しい文脈で実行し、結果を自分で読む。対照で失敗しないなら、直す必要はない。5回の結果がばらばらなら、言葉を足す前に書き方（上の表）を見直す。

devkit の流れに関わるスキル・エージェント（devkit-kickoff、devkit-run、implementer、reviewer、replanner）とランナー（scripts/devkit/）を変えたら、プラグインのリポジトリの `pnpm test`（偽の claude でランナーを通すテスト）を通し、、最後に小さなミッションを1つ、kickoff から完了まで流して確かめる。

## 仕上げのチェックリスト

- [ ] スキルなしの失敗を見た（記録がある）
- [ ] description は「いつ使うか」だけで、手順の要約がない
- [ ] 失敗の種類に合った書き方になっている
- [ ] スキルありで、同じ場面が守られることを確かめた
- [ ] 例は1つで、このリポジトリのスタックで書いた
- [ ] CLAUDE.md・README・`docs/devkit/` の関係する記述を直した
- [ ] ADR を書いた
