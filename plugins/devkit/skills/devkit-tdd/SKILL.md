# テスト駆動開発

テストを先に書き、失敗するのを見て、それを通す最小のコードを書きます。

**核心:** 失敗するのを見ていないテストは、正しいものを確かめているかどうか分からない。

## 鉄則

```
失敗するテストがない本番コードは書かない
```

テストより先に本番コードを書いてしまったら、消してテストから作り直す。「参考に残す」「テストに合わせて手直しする」もしない。

例外（使う前に利用者か、ランナーの作業なら goal と再計画の note で確認する）: 使い捨ての試作、生成されたコード（`drizzle/` のマイグレーション）、設定ファイル。

## サイクル

1. **RED: 失敗するテストを書く。** 1つの振る舞いを示す最小のテスト。名前は振る舞いを表し、受け入れ基準やビジネスルールなら番号を入れる。実物のコードを使う（モックは避けられないときだけ）。
2. **RED を確かめる（省略しない）。** `pnpm exec vitest run <テストファイル>` で失敗を見る。
   - 失敗のしかたが期待どおりか（機能がないから落ちている。書き間違い・import の誤り・構文エラーではない）
   - 最初から通ってしまったら、すでにある振る舞いを確かめている。テストを直す
3. **GREEN: 通す最小のコードを書く。** 先回りのオプションや機能を足さない。ほかのコードを「ついでに」直さない。
4. **GREEN を確かめる（省略しない）。**
   - そのテストが通る
   - **プロジェクト全体のテスト（`pnpm test`）も通る。** 自分のファイルだけ緑でも全体が緑とは限らない
   - 出力に警告やエラーが出ていない
   - テストが落ちたら、直すのはコード。テストではない。自分が原因でない失敗も、名前を挙げて報告する
5. **REFACTOR: 緑になってから整える。** 重複を除く、名前を直す、関数を切り出す。振る舞いは足さない。緑を保つ。
6. 次の振る舞いのテストへ。

### 例（このリポジトリのスタック）

```ts
// RED: 先にテストを書いて、落ちるのを確かめる
it("BR-1: 金額が 0 円の申請は拒否する", async () => {
  await expect(createExpense(db, { amount: 0, purpose: "出張" })).rejects.toThrow("1 円以上");
});
// pnpm exec vitest run tests/unit/expense.test.ts → 「createExpense is not a function」ではなく
// 「拒否されなかった」で落ちることを確かめてから、Zod スキーマに min(1) を足して通す
```

## よいテストの2原則

### 1. どの壊れ方を捕まえるかを言える

テスト本体を書く前に、**本番コードのどんな変更でこのテストが落ちるか** を言う。言えなければ、観察できる振る舞いに設計し直す。

- **期待値は手で求める。** リテラルや手で確かめた値を使う。テスト対象のコードや、その補助関数で期待値を計算しない（同じ計算同士の比較は必ず通る）。
  ```ts
  // ✗ 同じ関数で両辺を作っている
  expect(formatYen(1000)).toBe(formatYen(1000));
  // ✓ 手で求めた値
  expect(formatYen(1000)).toBe("¥1,000");
  ```
- **変更検知器を作らない。** 定数の値、文言の一字一句、内部の構造だけを確かめるテストは、意図した変更のたびに落ち、不具合には反応しない。その決定に依存する振る舞いを確かめる（`MAX_RETRY` が 5 であることではなく、「6 回目は試行されない」こと）。
- **自分のコードの境界を確かめる。** Server Action、ルートハンドラ、`src/server/` の関数、出力する CSV。Next.js や Drizzle そのものの仕組みは確かめない。

### 2. 実物を動かす

- **モックに対してアサーションしない。** モックがあれば通り、なければ落ちるアサーションは、部品について何も語らない。
- **DB は実物を使う。** `tests/helpers/test-db.ts` の `createTestDb()`（PGlite）を使う。モックしてよいのは、遅いもの・外部のもの（メール送信、外部 API、SSO）だけ。
- **モックする前に、実物の副作用を把握する。** テストが依存している副作用まで消さない。
- **モックの応答は実物の構造を完全に写す。** 一部のフィールドだけのモックは、後続のコードが別のフィールドを読んだときに黙って壊れる。
- **テストのためだけのメソッドを本番コードに置かない。** 後片付けなどは `tests/helpers/` に置く。
- **モックの準備がテストの半分を超えたら**、実物を組み合わせた結合テストに切り替える。

## 仕上げの変異チェック

テストファイルを書き終えたら、本番コードを頭の中で壊してみる。どの壊し方にも、落ちるテストが1つはあるべき。

- 定数や引数の誤り
- 分岐の取り違え
- 状態の更新・副作用の欠落
- 空や既定値を返す
- 0・空文字・null・権限なし・不正な形式の入力の検証漏れ

どのテストも落ちない壊し方があれば、その振る舞いは守られていない（またはテストが同語反復になっている）。

## 言い訳と現実

| 言い訳 | 現実 |
| --- | --- |
| 「単純すぎてテスト不要」 | 単純なコードも壊れる。テストは30秒で書ける |
| 「あとでテストを書く」 | あとから書いたテストは最初から通るので、何も証明しない。書いたコードに引きずられ、思いついたケースしか確かめない |
| 「手で動かして確かめた」 | 手の確認は記録が残らず、変更のたびにやり直せない |
| 「何時間分も消すのはもったいない」 | 使った時間は戻らない。信用できないコードを残すほうが無駄 |
| 「先に探索が必要」 | よい。探索は捨てて、TDD で始め直す |
| 「テストが書きにくい」 | 使いにくい設計のサイン。インターフェースを単純にする |

## 危険信号（見つけたらコードを消して TDD でやり直す）

- テストより先にコードがある
- テストが最初から通った
- なぜ落ちたのか説明できない
- 「今回だけ」「手で確かめたから」「趣旨は同じ」と考えている

## 困ったとき

| 困りごと | 対処 |
| --- | --- |
| 何をテストすればよいか分からない | 使いたい形の API を書き、アサーションから書く |
| テストが複雑すぎる | 設計が複雑すぎる。インターフェースを単純にする |
| 何でもモックしないと書けない | 結合が強すぎる。依存を引数で受け取る（`Db` を引数にしているのと同じ形） |
| 準備が大きい | 補助関数に切り出す。それでも大きければ設計を単純にする |

## バグ修正

不具合を見つけたら、まず不具合を再現する失敗テストを書き、このサイクルで直す。テストなしでバグを直さない。原因が分からないときは `devkit-debugging` を使う。

## 完了前のチェックリスト

- [ ] 新しい関数・振る舞いにテストがある
- [ ] それぞれのテストが、期待どおりの理由で落ちるのを見てから実装した
- [ ] 通すための最小のコードを書いた
- [ ] `pnpm test` がすべて通り、警告やエラーが出ていない
- [ ] テストは実物のコードを使っている（モックは避けられないものだけ）
- [ ] 境界値・エラーのケースがある（AC/BR の番号つき）
- [ ] 変異チェックで、捕まえられない壊し方がない
