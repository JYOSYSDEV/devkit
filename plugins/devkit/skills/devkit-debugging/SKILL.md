# 根本原因から直すデバッグ

**核心:** 直す前に、必ず根本原因を見つける。症状だけを直すのは失敗。

## 鉄則

```
根本原因を調べる前に修正しない
```

段階1を終えるまで、修正を提案しない。

急いでいるとき、「すぐ直せそう」に見えるとき、すでに何度か直そうとしたときほど、この手順を守る。手当たり次第に試すより、手順どおりのほうが速い。

## 4つの段階（順番に、前の段階を終えてから次へ）

### 段階1: 根本原因を調べる

1. **エラーメッセージを最後まで読む。** スタックトレース、行番号、ファイル名、エラーコードまで。答えがそのまま書いてあることが多い。
2. **確実に再現させる。** 正確な手順は何か。毎回起きるか。再現できなければ、推測せずにデータを集める。
3. **最近の変更を確かめる。** `git diff`、`git log`、依存パッケージや設定の変更、環境の違い（worktree とメインの作業ツリー、CI とローカル）。
4. **部品が複数ある場合は、境界ごとに証拠を集める。** 画面 → Server Action → `src/server/` → DB のように層があるとき、修正を考える前に、各境界で「入ったデータ」と「出たデータ」をログに出して1回動かし、**どこで** 壊れているかを特定してから、その部品を調べる。
5. **データの流れをさかのぼる。** 誤った値はどこで生まれたか。誰がその値で呼んだか。発生源まで上り、発生源で直す（`techniques.md` の「根本原因の追跡」）。

### 段階2: パターンを比べる

1. 同じコードベースの中で、似ていて正しく動くものを探す。
2. 参考にする実装があるなら、流し読みせず最後まで読む。
3. 動くものと壊れたものの違いを、どんなに小さくてもすべて書き出す。「それは関係ない」と決めつけない。
4. 依存しているもの（設定、環境変数、前提）を確かめる。

### 段階3: 仮説を立てて確かめる

1. **仮説を1つ、具体的に書く。** 「X が根本原因だと考える。理由は Y」。
2. **最小の変更で確かめる。** 一度に1つの変数だけ変える。複数を同時に直さない。
3. **確かめてから進む。** 当たれば段階4へ。外れたら、上に修正を重ねず、新しい仮説を立てる。
4. **分からないときは分からないと言う。** 知っているふりをしない。さらに調べるか、人に聞く。

### 段階4: 直す

1. **失敗するテストを先に作る。** もっとも単純な再現を自動テストにする（`devkit-tdd`）。
2. **根本原因に対して、修正を1つだけ入れる。** 「ついでに」の改善や、まとめてのリファクタリングをしない。
3. **直ったことを確かめる。** テストが通り、ほかのテストを壊しておらず、元の症状が消えている（`devkit-verification`）。
4. **直らなかったら止まる。** これまでに何回直そうとしたかを数える。
   - 3回未満: 段階1に戻り、新しい情報で調べ直す
   - **3回以上: 次の項目へ。4回目の修正はしない**
5. **3回以上直らないときは、設計を疑う。** 直すたびに別の場所で新しい問題が出る、直すには大きな作り直しが要る、という形なら、仮説の誤りではなく設計の誤り。人と相談する。ランナーが起動した実装担当なら、それ以上直さず `status: "blocked"` で報告し、`needs` に経緯と、何があれば進めるかを書く（ランナーが再計画に回す）。

## 原因が見つからないとき

調べた結果、本当に環境・タイミング・外部が原因だと分かった場合だけ、次を行う: 調べたことを記録する、適切な扱い（再試行、タイムアウト、エラーメッセージ）を入れる、次に調べられるようログを足す。ただし「原因なし」の大半は、調べ方が足りないだけ。

## 互いに無関係な失敗が複数あるとき

原因が別々で、直すファイルも重ならないことが確かなら、失敗ごとに調査をサブエージェントに任せて並列に進めてよい（それぞれに、対象の失敗、再現手順、変更してよいファイルを渡す）。同じ原因の可能性があるもの、同じファイルを直すものは並列にしない。並列のワーカー（implementer）の中ではサブエージェントを起動しない。

## こう考えたら段階1に戻る

- 「とりあえず直して、あとで調べる」
- 「X を変えて動くか試してみよう」
- 「いくつかまとめて変えて、テストを回そう」
- 「たぶん X だから直そう」
- 「よく分からないが、これで動くかもしれない」
- 調べる前に、直し方の一覧を書いている
- 「もう1回だけ」（すでに2回以上失敗している）
- 直すたびに別の場所で新しい問題が出る

## 言い訳と現実

| 言い訳 | 現実 |
| --- | --- |
| 「単純な問題だから手順は不要」 | 単純な問題にも根本原因がある。単純なら手順もすぐ終わる |
| 「急ぎだから手順を飛ばす」 | 手当たり次第より手順どおりのほうが速い |
| 「まず試して、それから調べる」 | 最初の修正が、その後のやり方を決めてしまう |
| 「直ったのを見てからテストを書く」 | テストのない修正は定着しない |
| 「まとめて直せば早い」 | どれが効いたか分からず、新しい不具合を生む |
| 「問題は見えている」 | 症状が見えているだけ。原因を理解したことにはならない |

## 早見表

| 段階 | やること | 終わりの目安 |
| --- | --- | --- |
| 1. 根本原因 | エラーを読む、再現する、変更を確かめる、証拠を集める | 何が・なぜ起きたか分かる |
| 2. パターン | 動く例を探して比べる | 違いが分かる |
| 3. 仮説 | 仮説を立て、最小の変更で確かめる | 当たったか、新しい仮説がある |
| 4. 修正 | 失敗するテスト、修正1つ、確認 | 不具合が消え、テストが通る |

補助の技法（根本原因の追跡、多層の検証、条件を待つテスト、テスト間の汚染の特定）は `techniques.md` を参照。
