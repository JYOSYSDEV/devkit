# devkit-kickoff: 依頼 → 仕様・計画 → 人の承認 → 自走

依頼: $ARGUMENTS

このスキルの成果物は **仕様書・計画ファイル一式** と **人の承認** です。ここではアプリのコードを書きません。実装は、承認のあとにランナー（`pnpm devkit run`）が作業ごとに AI を起動して行います。

仕組みは `docs/devkit/model.md`、計画の書き方は `docs/devkit/graph-rules.md` と `docs/devkit/goal-rules.md`、技術は `docs/devkit/stack.md` と `docs/standard/`（社内標準）にあります。最初に読んでください。記入例は `docs/devkit/examples/expense-app/` です。

## 役割の分担（話し方を変える）

| 役割 | 担うこと | このスキルで関わる場面 |
| --- | --- | --- |
| 業務担当者（依頼者） | 何を・なぜ作るか | 要件の聞き取り、仕様と計画の業務面の承認 |
| 標準オーナー | 社内標準・例外・技術ゲート | 計画の技術面の承認（運用レベル・認証・外部接続・個人情報） |
| AI（あなた・ランナーの AI） | どう作るか（社内標準の範囲で） | 仕様・計画の作成、承認後の実装 |

**技術のことを業務担当者に聞かない。** 技術は社内標準で決まっています。技術に関わる判断（運用レベル・ログイン方法・外部連携・個人情報）は、業務の言葉に言い換えて聞きます（`devkit-requirements` の「業務担当者が相手のとき」）。

## 0. 前提の確認

1. フォルダの状況を確かめる（`ls -a`、`git status`）。
   - **devkit が入っていない**（`scripts/devkit/devkit.mjs` がない）→ `devkit-init` スキルで用意してから戻る（空のフォルダなら新規作成、既存のアプリなら導入）。ホームディレクトリなどプロジェクトでない場所なら、フォルダ名を提案し、そのフォルダで `claude` を起動し直してから同じ依頼を出すよう案内して終える（そのフォルダの CLAUDE.md・設定・フックが効くように）。
   - **版の確認**: `node "${CLAUDE_PLUGIN_ROOT}/scripts/init.mjs" version --dir . --json` が不一致なら、`/devkit:devkit-update` で更新するよう利用者に伝えて止まる。
2. `pnpm -s devkit status` を実行する。
   - 計画がない → 1へ。
   - 計画が進行中 → 「既存の計画に追加する」か「新しいミッションとして始める」かを利用者に確認する。新しく始めるなら前のミッションを片付ける（完了済みなら `pnpm -s devkit archive`。未完了なら人が端末で `pnpm devkit archive`）。
   - ランナーが実行中（`ランナー: 実行中`）→ このスキルは計画を変えない。状況を伝えて終える。
3. 未コミットの変更があれば、それが何かを利用者に確認してから進める（勝手に捨てない）。

## 1〜2. 要件の聞き取りと仕様書

**`devkit-requirements` スキルを読み込み、その手順で** 要件を詰め、`docs/spec/<slug>.md` の仕様書を書き、読み合わせ（`spec-reader` エージェント）を経て、業務担当者に仕様書の内容を確かめてもらう。要点:

- 聞く前に、依頼文・既存コード・渡された資料を調べる。なぜ作るのかを最初に確かめる。質問は答えで作るものが変わるものだけを、1回に1問。
- 仕様書は `docs/spec/_template.md` の形式（FR / BR / AC、権限表、データモデル、画面と API、運用レベル、個人情報と外部連携、前提と未決事項）。AC は `- **AC-1** …` の形で番号を振る（ランナーは、この番号を名前に含み、実行されて合格したテストで照合する）。権限表の × は「権限なし」の AC にする。
- 業務担当者の答えから `docs/profile.json` を埋める（owners・tier・users・personalData・auth・externalHosts）。担当者の名前とメールは必ず確かめる（承認のときに照合する）。
- 自分が決めたことは「自分の判断」として前提に書く。非対話の実行では質問せず、推奨案で書き、判断をすべて前提に書く。

`devkit-requirements` の「規模を見積もる」で小さな変更と判断した場合は、計画を作らずに `devkit-tdd` で実装してよい。

## 3. mission を書く

`docs/devkit/templates/mission.md` を元に `.devkit/mission.md` を書く。完了の定義は「全マイルストーンの承認がそろう」（各マイルストーンでランナーが全体検証・受入基準の照合を行い、最後のマイルストーンではリリース前検査と最終レビューも行う）。

## 4. マイルストーン・作業・goal を設計する

`docs/devkit/graph-rules.md` に従い、`.devkit/graph.json`（version 2）を書く。要点:

- **マイルストーン = 業務担当者が1回で確認できる量。** 最初は基盤（`foundation: true`、承認者に technical を含める。データモデル・権限表・共通部品・認証の形を確定する）。最後は受入と本番準備（`release: true`、承認者は business と technical の両方）。
- **承認者（approvers）は計画で決める分だけ。** 外部接続・個人情報・権限表の変更・安全の中心・データモデルの変更は、ランナーが変更内容から見つけて承認者を足すので、「念のため全部に付ける」は不要。
- **作業（ノード）= 1つの goal。** 受入基準 2〜5個、変更ファイル 15 個程度まで。`acceptance` に担当する AC・BR を書き、仕様書のすべての AC・BR がちょうど1つのノードに割り当たるようにする。
- 並列に走りうるノード同士の `owns` を重ねない。共有ファイル・保護されたパス（`pnpm -s devkit shared`）は owns にできない。依存パッケージは `dependencies` に書く（許可リスト `docs/standard/dependencies.json` にあるものだけ）。
- E2E でしか確かめられない AC を持つノードは `verify: "full"` にする（そのノードの検証でビルドと E2E を回す）。そうでなければ、その AC はマイルストーンの全体検証で照合される。
- 外部の資格情報・費用・人の判断が着手前に要るノードは `before: ["technical"]` などを付ける。
- 雛形の見本（todos）を消すノードは、基盤のマイルストーンに置き、消すテストを `allowTestRemoval` に書く。
- 各ノードの `goal` は `docs/devkit/goal-rules.md` のテンプレートで書く（終了状態・証明方法・制約・ターン上限）。
- `limits`: `maxParallel` は 2〜3 から。`maxCycles` はノード数 × 2 程度。夜間に回すなら、業務ゲートが夜中に来て朝まで止まらないよう、マイルストーンの区切りを考える（必要なら `lookahead: true`。承認待ちの間も、次のマイルストーンの作業を先に進める。差し戻されると手戻りが増える）。
- `branch` は `devkit/<slug>`。

書いたら、エラーが0になるまで繰り返す:

```bash
pnpm devkit check
pnpm devkit mermaid --write
```

## 5. 独立レビュー

`plan-reviewer` エージェントに、仕様書のパスを伝えてレビューを依頼する。`blocking` が出たら直して 4 の検査からやり直す（最大2往復。直しきれない点は承認のときに伝える）。

## 6. 計画をコミットして、承認を依頼する

統合ブランチは **既定のブランチから** 作る（前のミッションのブランチの上に作らない）。

```bash
git switch <既定のブランチ> && git pull --ff-only     # リモートがなければ pull は省く
git switch -c <graph.json の branch>
git add docs/spec docs/profile.json .devkit
git commit -m "devkit: plan <slug>"
```

**業務担当者向け**（業務の言葉で、短く）:
1. 目的と範囲（作るもの・作らないもの）
2. 受入基準の件数と重要なもの3つ、権限表
3. マイルストーンと、確認をお願いする時期（業務ゲート）
4. 置いた前提

**標準オーナー向け**（同じ人なら1つでよい）:
1. 運用レベル・ログイン方法・外部接続・個人情報（profile.json）
2. 追加する依存パッケージ、標準の例外が要りそうな点
3. 技術ゲートの時期、並列数とサイクル上限

そのうえで、**承認は人が端末で行う** ことを伝える（Claude からは実行できない）:

```
pnpm devkit approve plan --role 業務    # 業務担当者
pnpm devkit approve plan --role 技術    # 標準オーナー
```

承認は計画の内容（graph.json・仕様書・mission.md）のハッシュに紐づきます。承認の後に計画を書き換えると、ランナーは動きません（もう一度承認が要る）。修正を求められたら 1〜5 に戻る。

## 7. 開始

両方の承認がそろったら（`pnpm -s devkit check` の最後に「計画: 承認済み」）:

1. `dependencies` があれば、利用者がいるうちに `pnpm add <名前…>`（開発用は `-D`）を実行する（確認が出るので、利用者がその場で許可する）。`pnpm verify` を通して `git commit -m "devkit: prepare <slug>"`。
2. `pnpm -s devkit start`（承認者のゲートとサイクル上限が記録される）。
3. `devkit-run` スキルでランナーを始める。利用者に、続けて見ているか、夜間に無人で回すかを聞く。

依頼文に「計画だけ」とあれば 6 で止める。
