# ADR-0004: claude-devkit の統治を取り込み、ランナーを実行の中心にしてプラグインで配る

- 状態: 承認待ち（標準オーナー）
- 日付: 2026-11-09

## 背景

社内には2つのキットがあった。

- **A: claude-devkit v2.0.0**（プラグイン）。社内標準を「規約・雛形・検査」で持ち、業務ゲートと技術ゲートを分け、変更内容から人の確認を足し、人の判断を記録する。実行は直列のランナー（`claude -p "/goal …"` を子として起動）。レビューで、ランナーの事後検査に「エージェントのコミットで基準がずれる」「`.npmrc` で verify を無効にできる」「実行されていない AC テストを数える」「落ちたときに改ざんを人の変更として記録する」などの重大な穴が見つかった。
- **B: devkit-template v3**（テンプレートリポジトリ）。依存グラフに沿った並列実行（dynamic workflow と worktree）、superpowers 由来の作法スキル、品質を重さで判定するレビュー、Stop フックでの自走、人間ゲートのコード化（controls.json・端末からの承認）を持つ。合否は LLM の verifier が判定し、制御は開いている対話セッションの中で回る。

要件として、(1) B をプラグインとして配る、(2) セッションを開いたままにせず夜間に無人で長時間回す、(3) 状態を確認できる、が加わった。利用者が示した構成案（ランナーが作業ごとに AI を呼び、検証・統合・完了をコードが決める）をもとに、レビューで挙げた7点（監視の置き場所、止まり方の区別、並列の待ち、統合の競合、承認済みの範囲の判定、停止条件、人間ゲートの抜け）を直して設計した。

## 決定

1. **B を土台にし、A の統治の仕組みを取り込む。** 取り込むもの: 社内標準（5層・rules.json・標準チェッカー・依存の許可リスト・例外の登録と期限）、案件プロファイル、業務ゲートと技術ゲート、変更検出による承認者の追加、判断の記録、判断依頼の書式（ESC-01〜05）、確認資料、役割別の通知、業務の言葉での聞き取り、安全な雛形（defineAction・権限表・入口のガード・監査）。
2. **実行の中心をランナー（コード）にする。** `pnpm devkit run` が作業ごとに `claude -p --agent devkit:<役割>` を起動し、AI が受け持つのは実装・レビュー・再計画の案だけにする。合否（クリーンな取り出しでの機械検証）・統合（クリーンなマージだけ）・状態の更新・承認者の決定・停止の判断はコードが行う。B の dynamic workflow と Stop フックによる outer loop、integrator エージェントは使わない（参考として `docs/reference-v3/` に残す）。
3. **完了の判定を二重にする。** ランナーの機械検証（範囲・保護パス・テストの弱体化・検証コマンド・テストの棚卸し・実行されたテストでの AC 照合・標準チェッカー）と、別の AI の独立レビューの両方に合格したときだけ統合し、統合後の検証にも合格したときだけ完了にする。A の「保護ファイルを戻す」仕組みは持たない（worktree の隔離と、統合前の検査で足りるため。A の重大な穴の原因だった）。
4. **人の判断は端末からだけ受け付け、記録する。** B の controls.json と端末からの承認を、役割（業務・技術）・担当者の照合・計画のハッシュ・検証したコミットへの紐づけに広げる。人のコマンドは controls.json だけに書き、ランナーが次の手で状態に反映する（ランナーの実行中でも安全）。
5. **計画は承認の時点で固定する。** 承認の後の変更は、ランナーが計画の差分を機械で分類して「承認済みの範囲」としたもの（記録を残す）か、人が承認した案だけ。
6. **夜間の無人実行と状態の確認をランナーに持たせる。** ロック、ハートビート、作業ごとの制限時間と予算、時間・費用・サイクル・進捗なしの停止条件、中断からの復旧、通知、状況ページ、実行のまとめ。/loop は人がいるときの案内役に限る。
7. **プラグインと案件で置くものを分ける。** スキル・エージェント・雛形の正本はプラグインに。ランナー・標準チェッカー・社内標準・ガード・権限は案件に版を固定してコピーし、版を照合する（プラグインでは権限を配れない。CI と無人実行でプラグインがなくても同じ判定をしたい）。

## 検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| A を土台に B の並列実行を入れる | プラグイン配布と統治がそろっている | A のランナーの作り直しになる（重大な穴の多くがランナーにあった） |
| B のまま（ワークフロー＋Stop フック）にプラグイン化と統治を足す | 変更が少ない。/workflows で並列の様子が見える | 制御が開いている対話セッションの中にあり、夜間の無人実行と両立しない。合否が LLM の判定に残る |
| **B を土台に、制御をランナー（コード）に移し、A の統治を取り込む（採用）** | 合否と制御がコードにそろう。セッションの外で動く。作業ごとにプロセスが分かれ、制限時間と予算を掛けられる | ランナーのコードが増える（テストで固める）。/workflows の代わりに status で様子を見る |

## 影響

- 計画の形式が version 2 になる（マイルストーン、受入基準の割り当て、承認者、着手前の承認、verify の種類）。v3 の計画は移せない（新しいミッションとして作り直す）。
- 承認は、v3 の「端末で approve」に、役割と担当者の照合が加わる。業務担当者と標準オーナーの名前とメールを `docs/profile.json` に書く。
- 1作業あたり、機械検証（依存のインストールと verify）がラウンドごとと統合後に走る。使用量は AI の呼び出し（実装・レビュー）が中心。
- 元に戻す方法: プラグインを v3 のテンプレートに戻す。案件の `.devkit/` は v3 の devkit.mjs からは読めない。
