# ADR-0005: 検証をコンテナで隔離し、AI の作業をリポジトリの外とサンドボックスに移す

- 状態: 承認待ち（標準オーナー）
- 日付: 2026-11-09
- 関連: ADR-0004（ランナーを実行の中心にする）

## 背景

v4.0 のレビューで、ADR-0004 の2つの保証が AI に対して守れていないことが分かった。

- **「完了はコードが決める」**: 機械検証の `pnpm verify` は、実装担当が書いたテストを、ランナーと同じ権限で、本体のリポジトリの中（`.devkit/worktrees/`）で実行していた。テストのコードから `.devkit/controls.json`（承認）・`graph.json`（計画）・`docs/decisions.md`（判断の記録）・テストの結果の JSON に手が届いた。実装担当が自分のセッションで実行する `pnpm test` も同じだった。
- **「人の判断は人だけが」**: 承認のコマンドは「端末から実行されたか」だけを見ていた。`script -qc` などの疑似端末で通り、ガードはパスの書き方（`./`・`cd`・glob）や包んだ書き方（`eval`・`sh -c`・`npm run devkit --`）ですり抜けられた。

利用者は「検証はコンテナで隔離して行う」と決めた。

## 決定

1. **検証コマンドはコンテナの中で実行する。** 対象のコミットを git の外の普通のフォルダに取り出し（`read-tree` と `checkout-index`）、コンテナ（Docker か Podman）にそのフォルダだけをマウントする。
   - 依存のインストールの段階: ネットワークあり、キャッシュ（pnpm のストアと pnpm 本体）に書ける。動くのは lockfile の依存と、人が管理する package.json の処理だけ。
   - 検証の段階: `--network none`、root 以外、読み取り専用のルート、`--cap-drop ALL`、`no-new-privileges`、キャッシュは pnpm 本体だけを読み取り専用で見せる。プロキシや認証の環境変数は渡さない。
   - 結果（`test-reports/`・画面写真）は、リンクをたどらず、取り出したフォルダの中の普通のファイルだけを読む。
   - 時間切れではコンテナを止める。落ちたランナーが残したコンテナは、次の起動で片付ける。
   - 範囲の外（共有ファイル・設定・リンク）を変えた作業は、検証コマンドを実行せずに不合格にする（検証そのものを変えられるため）。
2. **静的な検査はホストの取り出しで、リポジトリのコードを実行せずに行う。** 範囲・保護パス・テストの弱体化・リンクと入れ子のリポジトリ・標準チェッカー。標準チェッカーは本体の作業ツリーのもの（統合ブランチの版）を使い、取り出しの中のものは実行しない。
3. **AI の作業はリポジトリの外で、サンドボックスの中で行う。**
   - 実装担当の作業ディレクトリは、リポジトリの外の独立した clone（`~/.cache/devkit/<案件>/work/impl-*`）。ランナーはその中の `.git` を信用せず、本体の git ディレクトリと一時的な index でファイルを読んでコミットにする（AI が作業ディレクトリの git の設定を書き換えても、ランナーの git は影響を受けない）。
   - レビュー・再計画・最終レビューも、リポジトリの外の取り出しで行う。
   - AI の Bash は Claude Code のサンドボックス（`failIfUnavailable`・`allowUnsandboxedCommands: false`・ネットワークなし）で動かす。使えなければランナーは起動しない（`aiSandbox: "off"` で明示的に外せる）。
   - ガードとサンドボックスの設定は `--settings` で渡し、ガードは本体のリポジトリのものを使う。作業ディレクトリの写しのプロジェクト設定は読まない（`--setting-sources user`）。
   - （4.1.1 で追加）サンドボックスは Bash にしか効かず、Edit・Write は Claude Code の本体が書く。そこで、ランナーが作業ディレクトリを `DEVKIT_WORKDIR` で渡し、ガード（guard-edits・guard-bash）が実装担当の書き込み先をその中に限る（リンク・ハードリンク・`.git` の中も不可）。権限のルールでも、本体のリポジトリとホームの設定への Edit を断る。
4. **改ざんを検出する（封印）。** ランナーの実行中、承認・計画・判断の記録・devkit 自身のファイルが、ランナー自身と人のコマンド以外から変わったら、止まってコミットしない。人のコマンドは、書く内容のハッシュを先に `.devkit/journal.jsonl` に残してから書く。起動の前にも、記録と合わない未コミットの変更があれば断る。
5. **人のコマンドの確認を強める。** Claude Code の中から実行されたもの（環境変数・親のプロセス）を断り、端末で番号を打ち込んでもらう。担当者が空なら断る。マイルストーンの承認は、検証したコミットに紐づいたものだけを数える。ガードは、パスを解いてから（`cd`・`./`・`//`・`..`・絶対パス・glob・変数）判定し、包んだ書き方（`eval`・`sh -c`・`script`・`xargs`・インタプリタのコード・ヒアドキュメント）の中身も確かめる。
6. **CODEOWNERS とブランチ保護を必須にする。** 同じ利用者の権限で動くプログラムを完全には見分けられないため、承認の記録は人のレビューを通す。

## 検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| **コンテナで検証し、AI の作業はリポジトリの外とサンドボックスに（採用）** | 検証のコードから本体に届かない。ネットワークも切れる。Docker・Podman はどの OS でも使える | ランナーを回す機械に Docker か Podman と、Linux では bubblewrap が要る。検証ごとに依存のインストールが走る（キャッシュで短くする） |
| リポジトリの外の一時ディレクトリで検証するだけ | 追加の道具が要らない | 同じ利用者の権限なので、絶対パスで本体に届く。ネットワークも切れない |
| Claude Code のサンドボックスで検証も動かす | 道具が1つで済む | Claude Code のセッションの外（ランナー）からは使えない。OS ごとに挙動が違う |
| 承認を署名つきのコミット（ハードウェアの鍵）にする | なりすましを防げる | 利用者全員に鍵と運用が要る。今回は CODEOWNERS とブランチ保護で代える（将来の選択肢） |

## 影響

- ランナーを回す機械の前提が増える: Docker Engine 24 以上か Podman 4 以上、Linux・WSL2 では bubblewrap と socat（`docs/rollout.md` の 3・4）。
- 検証の時間: 検証ごとに、取り出し → 依存のインストール（ストアから） → 検証。pnpm のストアと node_modules は別のマウントにして、検証のコードがストアを書き換えられないようにする（ハードリンクを使わない）。
- 作業場所（`~/.cache/devkit/<案件>/`）にディスクを使う。ランナーは作業の終わりと次の起動で片付ける。
- v4.0 で記録した、検証したコミットのない承認は数えない（承認し直す）。
- 元に戻す方法: `isolation.mode: "none"` と `aiSandbox: "off"`（隔離なし。改ざんの検出は残る）。推奨しない。
