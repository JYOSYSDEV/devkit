# ADR-0007: Claude の出力の確認と承認を GUI から行う方法の検討（devkit コンソール）

- 状態: 方針決定（2026-11-10。実装前。下の「決定したこと」）
- 日付: 2026-11-10
- 関連: ADR-0003（人間ゲートをコードで守る）、ADR-0006（Supervisor とブリーフィング）、ADR-0008（標準オーナー向けのハブ）

## 背景

4.3.0 では、出力の確認と承認が次のように分かれている。

| すること | 今の手段 | 困ること |
| --- | --- | --- |
| 対話（聞き取り・仕様・計画づくり） | Claude Code のセッション | 特になし（デスクトップアプリ・VS Code でも同じスキルが動く） |
| 進み具合の確認 | `pnpm devkit status`・`.devkit/status.html`（30 秒ごとに読み直す静的なページ）・`logs` | 作業ごとの AI の出力（`.devkit/logs/run-*/`）・レビューの指摘・再計画の案の差分は、ファイルを開いて読む |
| 確認資料 | `.devkit/gates/<ID>.html`・`.devkit/briefings/*.md`・`.devkit/requests/<ノード>.md` | 置き場所がばらばらで、「今、自分が見るべきもの」に1か所からたどれない |
| 承認・差し戻し・回答 | Claude Code の外の端末で `pnpm devkit approve` など（番号の打ち込み） | 業務担当者に、端末・リポジトリの取り出し・git のメールの設定を求める。役割・依頼の ID・`--note` を手で打つ |

端末だけにしているのは便利さのためではなく、**AI が人の判断を出せないようにするため**である（`lib/human.mjs` の `requireHuman`: ランナーの AI でない・Claude Code の子でない・端末である・画面の番号を打ち込む）。GUI にするときは、この性質を保てる形だけを採る。

## 変えないこと

1. AI（対話の Claude・ランナーが起動した AI）は、人の判断を出せない。
2. 判断は対象の版（計画のハッシュ・検証したコミット・依頼の ID・ノードの定義）に紐づき、役割は受け付けるときと反映するときに確かめる。
3. 書き込みの経路は増やさない。GUI からの判断も、端末のコマンドと同じ関数で `controls.json`・journal・`docs/decisions.md` に書く。
4. 実行部品は依存パッケージなし（Node.js の標準の機能だけ）。プラグインがなくても、CI と無人実行で同じに動く。
5. 端末のコマンドは残す。

## 調べたこと（Claude Code の側。2026-11-10 時点の公式の文書）

| 項目 | 分かったこと | 設計への影響 |
| --- | --- | --- |
| プラグインが動く GUI | デスクトップアプリ（ローカル・SSH のセッション）と VS Code 拡張はプラグインに対応。JetBrains は端末で CLI を動かす形。claude.ai/code のクラウドのセッションは、リポジトリの設定からはプラグインが入らない | 対話の GUI は、すでにある。作らない |
| プラグインが自分の画面を持てるか | 一般の仕組み（パネル・Webview）は文書にない。VS Code 拡張だけ、プラグインの「mod」でペインなどを描ける | 特定の製品の画面に組み込むと、利用者の半分にしか届かない。画面はブラウザで出す |
| 自前の対話画面を Agent SDK で作る | 人の許可は `canUseTool` で受けられる。ただし、第三者の製品で claude.ai のログイン（サブスクリプション）を使わせることは、事前の承認がない限り認められておらず、API キーが前提 | devkit は「API の課金に自動で切り替えない」（ADR-0006）。自前のチャット画面は作らない |
| フックで承認を外に出す | `type: "http"` のフックと `PermissionRequest` がある。ただし、これは「ツールの実行の許可」であって、devkit の「業務・技術の判断」とは別のもの | 使わない。判断は devkit のコードが受ける |
| Claude Code の中かどうかの判定 | `CLAUDECODE=1` は、IDE 拡張が開く統合ターミナルにも付くと文書にある。Claude Code 自身が起動した子だけに付くのは `CLAUDE_CODE_CHILD_SESSION=1`（2.1.172 以上） | 今の `requireHuman` は `CLAUDECODE` で断るので、**VS Code の統合ターミナルで人が打った承認も断っている可能性がある**。実機で確かめ、判定を見直す（下の段階0） |

## 検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| A. 何も作らず、デスクトップアプリ・VS Code と端末で運用する | 変更なし | 背景の困りごとが残る |
| B. Claude との対話の中で承認する（質問のダイアログ・MCP の入力の要求） | 利用者には最も自然 | 承認が AI を通る。「変えないこと」の 1 に反する。**採らない** |
| C. VS Code 拡張（mod・Webview）に画面を作る | エディタの中で完結 | VS Code の利用者だけ。業務担当者は使わない。製品ごとに作り直しになる |
| D. 専用のデスクトップアプリ（Electron など） | 自由に作れる | 配布・更新・署名の運用が増える。依存パッケージなしの方針に合わない |
| **E. 案件の中のローカルのコンソール（`pnpm devkit ui`。ループバックだけの HTTP、ブラウザで開く）** | 依存なしで作れる。どの製品を使っていても同じ。既存の `computeStatus`・`buildBriefing`・`writeGateReport` をそのまま使える | ブラウザからの操作が「人」であることの確かめ方を、新しく決める必要がある（下） |
| **F. 承認は社内のハブで行う（ADR-0008。SSO と署名付きの決定）** | 本人の確認が今より強い。離れた場所から、複数の案件を判断できる | サーバーの運用が要る |

## 決定したこと（2026-11-10）

| 項目 | 決定 |
| --- | --- |
| 標準オーナー（技術の判断） | **ハブ**で確認して承認する（ADR-0008） |
| 業務担当者（業務の判断） | **案件の機械のローカルのコンソール**で確認して承認する（下の 3） |
| 署名 | どちらも、**判断する本人のパスキー（WebAuthn）**。案件の側は、同じ検証のコードで確かめる |
| 設定などの変更 | 変更が要る判断には**変更案を付けて見せ、承認されたら自動で当てる**（ADR-0008 の「変更案」。コンソールでも同じ形で見せる） |
| 対話の画面 | 作らない（デスクトップアプリ・VS Code をそのまま使う） |

## 提案する構成

### 1. コンソール（`pnpm devkit ui`）— 見る

- `node:http` で `127.0.0.1` のあいている番号に立て、URL を表示する（`--open` でブラウザを開く）。LAN には公開しない。夜間のサーバーの案件は SSH のポート転送で見る（離れた場所からの閲覧と判断はハブの役目）。
- 画面は1ファイルの HTML（外部の資源を読まない）。更新は Server-Sent Events（`.devkit/` のファイルの変更の通知＋定期の照合。Supervisor と同じ考え方）。`.devkit/status.html` はこれに置き換える。

| 画面 | 中身 | 元になるもの |
| --- | --- | --- |
| ホーム | 誰の番か・**自分の役割の判断待ち**・ランナーと Supervisor の状態・今日の使用量 | `computeStatus` |
| 計画 | 仕様書・依存グラフ（状態で色分け）・計画のレビューの指摘・承認の後の差分 | `graph.json`・`docs/spec/`・`mermaid` |
| 実行 | 作業ごとの時系列（実装 → 機械検証 → レビュー → 統合）・ラウンドごとの不合格の理由とレビューの指摘・AI の最終の出力・AI が自分で決めたこと | `state.json` の history・`.devkit/logs/run-*/`・`events.jsonl` |
| ゲート | 確認資料・受入基準と合格したテスト・変更検出のフラグ・リリース前検査 | `writeGateReport`・`.devkit/evidence/` |
| 判断依頼 | 何が必要か・なぜ・選択肢・おすすめ・対象の版 | `.devkit/requests/` |
| 再計画の案 | 計画の差分と、人の確認が要る理由 | `.devkit/proposals/`・`classifyPlanChange` |
| 履歴 | 判断の記録・ブリーフィング・実行のまとめ | `docs/decisions.md`・`.devkit/briefings/`・`reports/` |

- 判断待ちの項目には、**端末で実行するコマンドを組み立てて表示し、コピーできるようにする**（役割・依頼の ID・`--note` の入力欄つき）。この段階では、判断はまだ端末で行う。読み取りだけなので、Claude が起動してもよい（`devkit-status`・`devkit-gate-review` が案内する）。
- **AI が書いた内容の表示**: ログ・判断依頼・確認資料は AI が作ったもの。文字としてだけ表示し、確認資料の HTML はスクリプトと同一オリジンを許さない `iframe sandbox` で見せる。CSP でインラインのスクリプトと外部への接続を許さない。画面の中の文字列が「承認」の操作を起こせないようにするため、読み取りだけの段階から守る。

### 2. 判断の関数の切り出し（共通の土台）

今は `devkit.mjs` の各コマンドの中に、引数の解釈・人の確認（`requireHuman`）・検査・書き込みが一続きで書かれている。これを分ける。

```
lib/decisions.mjs   approvePlan / approveMilestone / approveBefore / rejectMilestone / answerRequest /
                    proposalAccept / proposalReject / exceptionAdd
                    … 入力は { 対象, 役割, 判断者, note, 人である証明 }。検査 → controls.json・journal・decisions.md
lib/human.mjs       人である証明（presence）を作る側:
                    tty（今の方式: 端末＋番号の打ち込み）／ passkey（コンソールとハブ。本人のパスキーの署名）
```

`decisions.mjs` は証明の種類を journal と `decisions.md` に残す（「端末」「コンソール（パスキー）」「ハブ（パスキー）・申請の ID」）。端末のコマンドの動きは変えない（既存のテストがそのまま通ることを条件にする）。

### 3. コンソールからの業務担当者の承認

ブラウザの操作は、端末と違って「同じ機械のプログラム（AI を含む）が HTTP で同じ要求を送れる」。そこで、**判断は本人のパスキーの署名で受け付ける**。署名には本人確認（生体か PIN）と本人の操作が要るので、同じ機械の AI には作れない。今の「端末＋番号の打ち込み＋git のメールの照合」より強い。

- コンソールは `http://localhost:<番号>` で開く（WebAuthn は `localhost` を安全な接続として扱い、パスキーは `localhost` に結び付く。`127.0.0.1` では使えない）。番号は `.devkit/config.json` の `console.port` で案件ごとに固定する。
- 判断の流れ: 画面で対象・役割・対象の版・確認資料（と、あれば変更案の差分）を見る → 承認・差し戻し・回答を選び、理由を書く → サーバーが決定の本体（ADR-0008 の封筒と同じ形）を作る → ブラウザが本体のハッシュを `challenge` にしてパスキーで署名する → サーバーが検証して、端末のコマンドと同じ関数（2）で反映する。封筒は `.devkit/decisions/` に保存してコミットする。
- 検証は、ハブの決定と同じコード（`lib/webauthn.mjs`）。公開鍵は `docs/profile.json` の `owners.business[].passkeys`、`origin` は `http://localhost:<console.port>`。本人確認（UV）が済んでいない署名は断る。
- 業務担当者が受け付けられる判断: 計画の業務の承認、マイルストーンの業務の承認と差し戻し、業務の判断依頼（ESC-03・04）への回答、業務の確認が要る再計画の案。技術の判断は、コンソールには表示とハブへのリンクだけを出す。

**パスキーの登録**（業務担当者ごとに1回）

1. 業務担当者がコンソールで「パスキーを登録」を押す（`navigator.credentials.create`）。
2. コンソールが、公開鍵を `docs/profile.json` に足す変更案（`profile.owners.passkey.add`）を作る。
3. 標準オーナーがハブで、だれの鍵かを確かめて承認する。承認されたら、案件の側で自動で当たる。
4. ハブをまだ置いていない間は、標準オーナーが端末で `pnpm devkit owner passkey accept <登録の ID> --role 技術` を実行する。

**守るもの**

| 危険 | 対策 |
| --- | --- |
| 同じ機械の AI が、判断の API に要求を送る | パスキーの署名がなければ受け付けない。ガード（guard-bash）でも、Claude のコマンドからコンソールへの送信を止める。ランナーの AI はネットワークなしのサンドボックスの中 |
| 画面の中の AI の文章が、承認の操作を起こす | 1 の表示の規則（文字としてだけ表示・`iframe sandbox`・CSP）。署名には本人の操作が要る |
| ほかのページ・ほかの機械から | `Host`・`Origin` を確かめる。`localhost` だけで待ち受ける。CORS を許さない |
| 古い判断・別の対象への使い回し | 決定の本体に、案件・対象・対象の版・期限を入れる。同じ決定は1回だけ反映する（ハブの決定と同じ） |
| 見せた内容と違うものに署名させる（コンソールの偽物。別のプログラムが同じ番号で待ち受けて、偽の画面を出す） | 完全には防げない。コンソールは業務担当者が自分で起動する（スキルは起動のしかたを案内するだけで、Claude は `--decide` で起動できない）。決定の本体は検証のときに今の状態と照合するので、偽の画面で作れるのは「今、実際に判断待ちの対象への決定」だけ。封筒が git に残り、CODEOWNERS とブランチ保護を併用する |

**前提**: コンソールは、案件の作業ツリーがある機械で動かす。業務担当者はその機械のブラウザで開く。夜間のサーバーで回している案件は、SSH のポート転送で自分の PC のブラウザから開く（`localhost` のまま届くので、自分の PC のパスキーで署名できる）。

## 段階

| 段階 | 入れるもの | 信頼の変化 |
| --- | --- | --- |
| 0 | 判断の関数の切り出し（`lib/decisions.mjs`）。WebAuthn の検証（`lib/webauthn.mjs`）と変更案（`lib/changes.mjs`）の形式とテスト（ADR-0008 の段階0と共通）。`requireHuman` の判定の見直し（VS Code の統合ターミナルで人が打った承認が断られるかを実機で確かめる） | なし（端末のコマンドの動きは変えない） |
| 1 | 読み取りだけのコンソール（7画面・SSE・コマンドの組み立てとコピー）。`status.html` の置き換え。スキルの案内 | なし |
| 2 | 業務担当者のパスキーの登録と、コンソールからの業務の判断。変更案の表示と自動の適用 | 業務担当者のパスキーが、判断の経路に加わる |
| 3 | コンソールの判断待ちに、ハブの申請へのリンクと状況を出す（ADR-0008 の段階2の後） | なし |

## 段階0の実装（2026-11-10）

ADR-0008 の「段階0の実装」のとおり（`lib/decisions.mjs`・`lib/webauthn.mjs`・`lib/envelope.mjs`・`lib/changes.mjs`）。業務担当者の署名は、`origin` が `http://localhost:<console.port>`、公開鍵が `docs/profile.json` の `owners.business[].passkeys` のときだけ通る。

`requireHuman` の判定の見直し（VS Code の統合ターミナル）は、実機での確認が要るので入れていない。

## 残っている確認

1. 業務担当者が使う機械とブラウザ（パスキーは、端末の生体認証か、セキュリティキーか。会社の PC で WebAuthn が使えること）。
2. VS Code の統合ターミナルからの端末のコマンドを認めるか（実機で確かめた結果による）。
3. コンソールに出す AI の生のログの範囲（全文か、要約と最終の出力だけか）。

## 影響

- 実行部品: `lib/decisions.mjs`・`lib/webauthn.mjs`・`lib/changes.mjs`・`lib/console.mjs`（サーバー）・`lib/console.html`（画面）を足す。`docs/profile.json` の `owners.business[]` に `passkeys` を足す。`devkit.mjs` の人のコマンドは、切り出した関数を呼ぶ形になる。
- ガードと権限: 判断の API への送信と `ui --decide`・`owner passkey accept` を、Claude のコマンドから止める規則。封印の対象は変わらない（`scripts/devkit/` に入る）。
- 文書とスキル: `devkit-status`・`devkit-gate-review`・README・rollout.md。
- テスト: 偽の claude を使う既存のテストに、コンソールの API（読み取り・署名の検証・使い回しの拒否・`Origin` の拒否・AI の文章の無害化）を足す。WebAuthn は、試験用の鍵で作ったアサーションで確かめる。
- 元に戻す方法: `pnpm devkit ui` を使わない。状態にも記録にも、コンソールだけが持つものはない。
