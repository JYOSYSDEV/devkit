# ADR-0006: 自律運用の拡張（定時ブリーフィングと Supervisor）。技術提案書の検討結果

- 状態: 承認待ち（標準オーナー）
- 日付: 2026-11-09
- 関連: ADR-0004（ランナーを実行の中心にする）、ADR-0005（検証の隔離）
- 検討した提案: 「devkit 自律運用機能拡張 技術提案書」（2026-11-09、対象 v4.1.0）

## 背景

v4.2 までは、夜間に止まった作業を朝に人が判断しても、だれかが `pnpm devkit run` を打つまで続きが進まなかった。朝の報告は、実行ごとのまとめ（`.devkit/reports/run-*.md`）を人が読み比べる必要があった。提案書は、(1) 夜間の成果・今朝の判断・判断後に進む作業を1通にまとめる定時ブリーフィング、(2) 判断を受けた自動再開と、障害の分類による限定的な再試行、(3) 事前許可の範囲での自己修復、を段階0〜4で導入することを求めた。

## 検討の結果

| 段階 | 提案 | 4.3.0 での扱い | 理由 |

| 0 前提整備 | 承認・保護ファイルの経路、役割判定、証跡の失効の補修 | **採用**（4.2.0 と 4.3.0） | 自動再開は、偽の判断で動かないことが前提。4.2.0 で役割の一致と git の書き込みを直し、4.3.0 でコミット済みの改変・着手前の承認の失効・検証コンテナの追加引数を直した |

## 決定（段階0〜2）

### 承認の保護と失効（段階0）

1. **コミット済みの改変も止める。** `state.json`・`controls.json`・`docs/exceptions.json` は、devkit のコマンド（journal に記録が残る）とランナー（コミットのたびに journal に記録する）だけが書く。ランナーは起動の前に、今の内容がそのファイルの journal の**最後の**記録（か、それより後に前回のランナーが書いた内容）と合うかを確かめ、合わなければ起動しない（コミットしてしまえば受け入れられる、という抜け道を塞ぐ）。journal もコミットされるので、`git revert` で記録ごと巻き戻せる。そこで journal の行数とハッシュを手元（コミットしない）に残し、今の journal がそれを伸ばしたものであることも確かめる。人が内容を確かめた上で受け入れるときは、標準オーナーが端末で `pnpm devkit seal accept` を実行し、判断の記録に残す。
2. **着手前の承認はノードの定義に紐づける。** 再計画でノードの定義（goal・owns・依存など）が変わったら、着手前の承認は取り直しになる（マイルストーンの承認は検証したコミット、計画の承認は計画のハッシュ、判断依頼の回答は依頼の ID に、すでに紐づいている）。
3. **検証コンテナの追加引数は許可リストで正規化する。** 資源の上限・ラベル・`KEY=値` の環境変数だけ（インストールの段階は `--add-host`・`--dns` も）。ネットワーク・権限・マウント・利用者・読み取り専用の解除は、どの書き方でも足せない。

### 定時ブリーフィング（段階1）

1. 毎日 `briefing.time`（既定 08:00、`Asia/Tokyo`）を締切にし、前回の締切から今回の締切までを集計する。締切は配信が遅れても動かさず、遅れと実際の作成時刻を書く。
2. **夜間の成果は、封印された `state.json` から決める**（ノードの統合の時刻・マイルストーンの検証と承認の時刻・ミッションの完了）。完了は1つのノードに1つの記録なので、再起動をまたいでも重複しない。完了の累積値は成果として扱わない。運用の出来事（実行の開始・終了・断った起動・再試行・停止・配信）は `.devkit/events.jsonl` に ID 付きで追記し、ID で重複を除く。
3. **判断後に進む作業は、ランナーと同じ判断（`decide`）を、判断を入れた写しの状態で求める。** 説明用の推測ではなく、実際にランナーが次に始める作業を書く。判断を待たずに進む作業も分けて書く。所要時間は実績がないので書かない。
4. 文章は構造化データから決まった形で作る（AI は使わない。AI が使えなくても作れる）。秘密値の形の文字列は伏せ、生ログは載せない。保存先は `.devkit/briefings/<日付-時刻>.md` と `.json`。
5. 送信は送信待ち（`.devkit/cache/supervisor/outbox/`）に入れ、配信キー（案件・締切・送り先）で2回送らない。失敗したら間隔をあけて送り直し、上限を超えたら failed にする（保存したものは残る）。送り先は既存の通知のコマンド（`DEVKIT_NOTIFY_CMD` など）を1つ使う。

### Supervisor（段階2）

1. **Supervisor は「今ランナーを1つ起動してよいか」だけを決める。** 実装の判断・検証・統合・人の決定の反映はランナーのまま。計画・承認・検証の正本は既存の記録に置き、Supervisor の管理情報（`.devkit/cache/supervisor/`）は承認の台帳にしない。
2. **起動の条件**（起動の直前にもう一度確かめる）: ランナーが動いていない・状態が進行中（一時停止・停止・完了でない）・計画が承認済み・記録に不整合がない・再試行の待ちの時刻を過ぎている・時間帯の中・日ごとの上限の中・進捗なしの起動が続いていない・**人の決定を反映した写しの状態で、実行できる作業がある**。誤った役割の判断や古い版への承認は、反映のときに捨てられるので作業が増えず、起動しない。
3. **検知**: `controls.json` の変更の通知（ファイルの監視）と、`intervalSeconds`（既定 20 秒）ごとの照合。通知を取りこぼしても、照合で拾う。通知の返信だけで承認済みにはしない（判断は既存の CLI だけ）。
4. **終了の分類**: 一時的な障害（通信・5xx・応答なし）は指数的な待ち＋揺らぎで最大3回（`retry.maxAttempts`）・合計の期限つき。利用上限は復帰の時刻が分かればその後に再開し、分からなければ止まる。認証・環境の問題は報告して止まる。保護された記録の不整合は、すぐ止めて証拠を残し、すぐ知らせる。試行回数・日ごとの起動回数と使用量は手元の記録に残し、Supervisor を起動し直しても数え直さない。
5. **止まった状態**（上限停止・環境の停止・方針違反・手動停止）は、Supervisor が自動では解除しない。標準オーナーが原因を直してから、端末で `pnpm devkit supervisor clear` を実行する（判断の記録に残る）。手動停止は `pnpm devkit supervisor stop`（だれでも）。止めてもブリーフィングは続ける。
6. **課金**: API の課金に切り替わる設定（`ANTHROPIC_API_KEY` など）は、`supervisor.allowApiKey` を明示しない限りランナーに渡さない。利用上限では待つだけで、別の課金に切り替えない。使用量の金額は API 料金で換算した目安と書き、実際の請求額やサブスクリプションの残りと区別する。
7. 単一ホスト・単一案件。OS のサービス管理（systemd・launchd）で Supervisor を動かし続ける（docs/rollout.md）。Supervisor が落ちても、起動したランナーはそのまま続き、次の Supervisor が終了の記録を照合する（記録なしにいなくなったランナーは、落ちたものとして再試行の対象にする）。

## 段階3（自己修復）を入れるときの条件

段階0〜2の運用で、次を実測してから別の ADR で決める: 判断待ちの理由のうち「依存の追加」が占める割合、自動再開の誤起動・取りこぼしが 0 件であること、改ざんの検出の誤検知の頻度。入れる場合も、次は変えない。

- AI のワーカーには共有ファイルの書き込みを渡さない。AI は修正案（差分）を出し、ランナーの保護された実行部が検査して、事前許可のレコード（許可 ID・承認者と役割・対象・操作とパス・依存名と版・期限・必須の検証・失効の条件）に一致するものだけを専用のブランチで当てる。
- 最初の対象は、版まで固定した依存の追加だけ。DB の変更・認証と権限・依存の無制限な更新・秘密情報・承認の台帳・検証の仕組み・社内標準・受入基準・上限は対象にしない。テストや合格条件を弱める変更は断る。
- 当てた後は必須の全体検証を通し、計画の変更で影響する許可は再評価する。

## 結果

- 夜間に止まった判断に朝答えれば、Supervisor が続きを進める。人は朝の1通で、成果・判断・判断後の見通しを確かめられる。
- 新しく動くものは Supervisor だけで、ランナー・検証・承認の経路は変えていない。新しい書き込みの経路（共有ファイルの自動変更）は作っていない。
- 本番導入の前に、実際の Claude Code の認証・隔離の環境・通知先を使った試験が要る（提案書の受入基準。リポジトリの試験は偽の claude とコンテナで行っている）。
